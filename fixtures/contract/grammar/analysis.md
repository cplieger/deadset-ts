# The analysis

This page states the rules every analyzer applies to decide what the program is, which of it is test code, what is live without a reference, what a type error withholds, which failures end a run and which hints a report carries. A rule here holds for both languages unless it names one. The vocabulary the rules report in is [`kinds.json`](../kinds.json), the configuration keys they read are [`config.schema.json`](../config.schema.json), the report members they fill are [`report.schema.json`](../report.schema.json) and the exit codes they end with are [`exit-codes.json`](../exit-codes.json).

Every rule on this page that adds a root, a use or a retention only ever makes a subject live: no such rule turns a live subject dead, and none raises a finding's severity or confidence. A file such a rule makes live is judged member by member: the file is no longer reported, and each of its declarations is reported or held as its own references decide, so the one finding about the file may give way to findings about the declarations it holds. The rules that end a run end it before any finding list exists.

## The program

The program is the source the analysis holds for the target and its declared consumers under each configuration of the run. A run that holds no program, a target with no source file of its language or a configuration that names no file, ends with exit code 3.

### Component files

A file whose name ends with an extension `ts.component_extensions` lists is a component file. A component file is in a project's program when the project's file list names it or an import of the program resolves to it, and an import of a component file resolves to that file. The analysis reads a component file as markup holding script blocks, and it parses no markup:

- A `<script>` element whose start tag begins a line at the top level of the file is a block. Its content, up to the matching `</script>` end tag, is source of the language its `lang` attribute names: `ts` and `tsx` are TypeScript, and a block with no `lang`, or with `js` or `jsx`, is JavaScript.
- A file whose first line is `---` holds a frontmatter block: the lines after it up to the next line that is `---` are a TypeScript block.
- A `<script>` element with a `src` attribute, in its self-closing form or with an end tag, is a namespace import of the file `src` names, positioned at the attribute. It references every export of that file, as a retained namespace import binding does.
- The blocks of one file are one module, read in file order, of the strongest language any block names, in the order TSX, TypeScript, JSX, JavaScript. A file that holds no block is an empty module.
- A `<script` start tag that begins a line and is not read as a block, or that begins a line inside a block, is printed as a warning on standard error naming the file and the line, and the file is analyzed without it.

Every top-level binding of a component file's module is retained while the file is live, because the markup may use it: a declaration, and an import binding, which is resolved to the declaration it names, a namespace or default import to the module or the export it names. No finding is reported about a retained binding, `DS1104` included. Everything the module references counts as a use. The markup of a live component file is template text for the `template-field` exemption of [`exemptions.json`](../exemptions.json), so a member whose name the markup holds is retained by that class. A type error in a block is a type error under the rule below.

### Workspace packages

A TypeScript workspace is declared by the `packages` sequence of a `pnpm-workspace.yaml` file, or by the `workspaces` member of a `package.json`, an array of globs or an object whose `packages` member is one. The analysis searches for the declaration from the target root upward to the first directory holding one, and no further than the root of the repository that holds the target. A member is a directory the globs name, minus the globs a `!` negates and never under a `node_modules` directory, that holds a `package.json` with a `name`; the directory holding the declaration is a member too.

An import whose package name is a member's resolves to the member's source, so a workspace is analyzed with no build and no path mapping:

1. Where the package manager linked the importing directory to another package of that name, and that package is not the member, the import keeps the resolution the compiler gives it, and so does an import from outside the member that the member's name does not link.
2. Otherwise, where the compiler's own resolution reaches a source file inside the member, that file stands. A declaration file stands only when no configuration of the member writes its output where the file is.
3. Otherwise the member's manifest decides: the `exports` entry the import's subpath selects, the exact key first and then the longest pattern, its targets tried in condition order; with no `exports`, `types`, `typings`, `main` and `module` for the package itself, or the subpath below the member's directory. Each target is read back to its source through the member's emit mappings: each compiler configuration of the member maps its output directory and its declaration directory to its root directory, or, with no root directory, to the configuration's own directory and then to the common directory of its input files, and an output file maps to the source file of the same name with the source extension the output extension stands for.
4. An import no candidate reads back to a source file is the setup failure `workspace-member-without-source` below.

A reference from every program that holds a member's file counts, so a declaration a sibling member uses is live. A finding about a member's file is reported only from a configuration that owns the file, one whose own file list names it; a configuration that holds the file only because an import reached it contributes references to it and no verdict about it. A member's manifest entries are roots as the target's own are, published unless the member's manifest marks it private.

## Test code

Test code is the test files and the test-support code. A test file is a Go file whose name ends with `_test.go`, and a TypeScript file `ts.test_files` names. A test is a declaration of a test file, a test function the test runner calls among them. Test-support code is the code only tests reach: the largest set of Go packages and TypeScript files, none of them a test file, such that a test reaches each member, no member holds a root, and every import of a member and every reference to a declaration of a member from outside it is written in a test file or in another member. A reference here is a name that resolves to the declaration, so a call through an interface method or a function value references no implementation. A Go package is here its files other than test files, so a reference from its own test files is from outside it. A test reaches a package or a file through a chain of imports and references that starts at the test, whatever members the chain passes through. So every chain that reaches test-support code starts at a test, however many members lie between: a package only another member imports is test-support code, and so is a package whose only users are its own test files. Production code a test calls stays production code, because a chain from production code or from a root reaches it too. A Go `init` function and a blank declaration run because their package is loaded, so neither is a root for this rule. A Go package or a TypeScript file a library's published API reaches is not test-support code, because outside programs may import it. The analysis classifies code by the chains that reach it and does not judge whether a test is a good one, so a test that reaches no production code is not reported for that.

Test code is judged with the tests:

- A reference from test code is a test reference, and a production sweep, which counts no test reference, judges no declaration of test code.
- A test function the test runner calls is a root. In Go it is a test, a benchmark, an example or a fuzz test of a test file, or `TestMain`. In TypeScript the runner loads a test file and calls what its top level registers, so the file's top level and every declaration its export table names are roots. Such a root is reported only under `DS1005`. A Go `init` function and a blank declaration of a test file are roots as they are in production code, because they run when the test binary loads their package. Neither is judged under `DS1005`.
- A declaration of a test file that is no root is reported under `DS1005` where that kind's rule holds for it. Otherwise it is reported when nothing references it, under the code a production declaration with the same shape carries: `DS1201` for an interface and the unused code its visibility selects otherwise. A declaration of a test file that only reported declarations of test files reference falls with them, in their dead component. A production declaration such an unreferenced declaration references stays out of that component: its own references decide its code and its component, and the reference counts as a test reference.
- A declaration of test-support code is reported under `DS1005` where a declaration of a test file would be. Otherwise it is not dead while test code references it, and it is reported at reachability class `possible` under the code a production declaration with the same references carries, `DS1201` for an interface and `DS1004` otherwise, in every target kind and in both Go test styles, a test file of its own package or of an external test package. When nothing references it, it is reported at `certain` under the code a production declaration nothing references carries, `DS1201` for an interface and the unused code its visibility selects otherwise. Such a `possible` finding belongs to no dead component, so its component is minted for it, with the subject as its one root member, an interface's members falling with it as `DS1201` states and no deletable line, and test-support code is no target symbol when `DS1005` judges a test or a declaration of test-support code, so a test whose every reference is to test-support code has an empty set and is not reported.
- A part of a declaration of test code, a parameter, a receiver, a result, a statement, a store or a case, is reported only while the declaration is live in the run that counts test references. A TypeScript part that no declaration holds, written in a file's top-level statements or in a function they pass or hold, belongs to the file and is judged while the file is live, so the parts of the callbacks a test file registers are judged in the run that counts test references, as the body of a Go test function is. A declaration of test code nothing live references is not judged, so none of its parts is reported, and a declaration of test code reported under `DS1005` or as unreferenced is reported whole.

A file the analysis classified as test-support code is counted in the report's `test_file_rules` under the rule `test-support`.

## Uses through memory layout

In Go, a conversion of a pointer to `unsafe.Pointer`, or of an `unsafe.Pointer` to a pointer type, reads and writes every field the pointed-to type lays out, recorded at the conversion: every field of it where it is a struct type, every field of its element type where it is an array type, and so on through every field of a struct type and every element of an array type it holds, at any depth. A field or an element holding a pointer, a slice, a map, a channel, a function or an interface is itself read and written, and the use goes no further into the storage it refers to, which the pointed-to type does not lay out. Where the pointed-to type is a type parameter, or a struct or array type that holds one at any depth, the conversion has the same use of each type argument that type parameter takes in an instantiation the program holds, an instantiation made through another generic declaration's own type parameters included, because the instantiated type is the one the conversion lays out. A struct type that declares a field of type `structs.HostLayout` has the same use of every field it lays out, recorded at that field, because its layout is fixed for code outside the program. Code that reads memory through either names no field, so no field such a use reaches is reported under `DS1003` or `DS1301`.

## References in TypeScript

### Module URLs

In a source file of the program, `new URL(<string>, import.meta.url)`, where `URL` names no declaration of the target, and `import.meta.resolve(<string>)`, with the string a string literal or a template literal with no substitution that starts with `./` or `../`, name the file the string resolves to against the file's own directory, as a relative specifier of a configuration file resolves. A runtime starts that file as a module, a worker among them. The expression is an import of the file for its effects, written in the file that holds the expression: the file joins the import graph there, its top level is live while the holding file is, and no export of it is referenced. A file only test code loads this way is test-support code.

### Module namespace objects

A module namespace object is the binding of a namespace import, `import * as ns`, the value an `await` of a dynamic `import()` produces, the first parameter of the first callback passed to `then` on a dynamic `import()` call, and the binding of a `const` declaration whose initializer is one of these. A dynamic `import()` names a module when its argument is a string literal or a template literal with no substitution that the program's module resolution maps to a source file. A use of a namespace object references the module's exports by what it reads:

- A property access by name, `ns.name`, or by an index that is a string literal or a template literal with no substitution, references the export of that name, a re-export walked to the declaration it carries, and so does each property an object binding pattern destructures from the object.
- Any other use references every export of the module, because code the analysis does not follow may read any export through the object: the object or the `import()` call passed as an argument, returned, assigned to anything but a `const` binding, stored in a property or an element, spread, or indexed by any other expression, a `typeof` query of it included.
- A namespace object nothing uses references no export, and neither does a dynamic `import()` whose value is not used, being an expression statement, a `void` operand or an `await` whose result is not used: the call loads the module and nothing more.

### Module declarations

A `declare module` declaration whose name is a string literal, an augmentation of a module in a module file or an ambient module declaration in a script, is referenced by each import of the program that names its module. An import names the module when its specifier equals the declaration's name or when both resolve to the same source file. Where the declaration's name holds one `*`, an import names it when its specifier matches the name with the `*` standing for any run of characters. An import here is an import or a re-export declaration, a dynamic `import()` whose argument is a string literal or a template literal with no substitution, an `import x = require()` declaration and an import type, in any file of the program, the declaration's own file included. The reference is recorded at the import and held by the declaration that holds it, or by the file where the import is a top-level statement. A module declaration no import names is reported whole under `DS1002`, and its members fall with it. While an import names it, each member of the declaration is judged as any other member of the program is, by its own references.

### Overrides of outside classes

A method of a class of the target that overrides a member of a class declared outside the target and its loaded consumers, in the compiler's library declarations or in a dependency, at any depth of the class's `extends` chain, is called by code outside the analysis that holds the instance through that class. The method counts as referenced by the class that declares it, so it is live while that class is, it falls with the class when the class is dead, and it is never reported under a code of its own as unused.

### Members reached through types

A value reaches a position typed by a type when it initializes or is assigned to a declaration, a property, an element or a parameter that type annotates, when a function whose result type annotates returns it, and when a `satisfies` expression checks it against that type. An `as` expression is no such position. Where the value's type and the position's type differ, the value's type reaches the position's type, and a pair of types reaches as follows:

- An object type reaching an object type reads each member of the first that the second declares under the same name, because the compiler reads the member to check the assignment and code holding the position reads it through the position's type. A union or an intersection on either side is compared constituent by constituent, and a constituent of the value's type that is a constituent of the position's type reads nothing.
- An array or a tuple reaching an array or a tuple reaches through its element types. A function type with one call signature reaching a function type with one call signature reaches through its signature: each parameter type of the position's signature reaches the parameter type in the same place of the value's signature, and the value's result type reaches the position's result type.
- A pair reaches once, so the walk ends when no pair joins.

A property of an object literal writes the member of its contextual type that `DS1301` in [`kinds.json`](../kinds.json) names, and a read of that property through a value of the literal's own type, a declaration the literal initializes without an annotation included, reads that member.

A value whose type is declared outside the target and its loaded consumers, in the compiler's library declarations or in a dependency, that reaches a position typed by an object type of the target reads each member of the target's type that the value's type declares under the same name, because code outside the analysis holds the value and reads those members.

### Indexed-access types

An indexed-access type `T[K]` whose index type `K` is a literal type, a string literal type or a numeric literal type, or a union of literal types, references each member of `T` that one of those literals names, as a property access by that name does. The reference is recorded at the indexed-access type and held by the declaration that holds it. Where `K` is a type parameter of the function or method a call calls, the call references each member of the type `T` stands for in that call that a literal of the type argument the call fixes for `K` names, where that type argument is a literal type or a union of literal types, whether the call writes it or the compiler infers it from the call's arguments. That reference is recorded at the call and held by the declaration that holds the call. An indexed-access type whose index is any other type references no member under this rule.

## Roots

A root is live without a reference. Beside the roots `roots.patterns` and `ts.entry_files` configure, the entry points a manifest names and a library's published API, the TypeScript analysis marks the roots below. A root that names a file roots the file's top level and everything its export table names, a re-export walked to the declaration it carries, and is live under both liveness relations, because a program the project runs loads it.

### Configuration files by name

A file in a directory that holds a `package.json` is a configuration file when its name is `<stem>.config.<ext>` or `<stem>.<qualifier>.config.<ext>`, with `<ext>` one of `js`, `mjs`, `cjs`, `ts`, `mts` and `cts`, or `.<stem>rc.<ext>`, with `<ext>` one of `js`, `mjs` and `cjs`. `<stem>` and `<qualifier>` are each a run of letters, digits, hyphens and underscores. A configuration file in the program is a root. A configuration file no program holds is read all the same, with no type information and no declaration of it judged: its strings are read under the rule below, the specifier of each of its imports and re-exports among them, so an import naming a dependency is a use of the dependency. A file such a file imports by a relative specifier, that no program holds either, is read the same way, and so on until no further file joins. Such a relative specifier resolves against the importing file's directory to the first of these paths that names a file:

1. The path the specifier names, where its name ends with one of the extensions of step 3.
2. That path with a final `.js` replaced by `.ts` and then by `.tsx`, a final `.jsx` replaced by `.tsx` and then by `.ts`, a final `.mjs` replaced by `.mts`, or a final `.cjs` replaced by `.cts`.
3. That path with `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs` appended, in that order.
4. Where the path names a directory, the file `index` in that directory with the extensions of the previous step appended, in the same order.

A specifier that reaches no file adds no file and raises no setup failure. A specifier that names a file of another kind, a `package.json` or another JSON file among them, reaches no file, so the strings of a manifest a configuration file imports use none of the dependencies it declares.

A JSON configuration file is a file in a directory that holds a `package.json` whose name is `<stem>.config.json`, `<stem>.<qualifier>.config.json`, `.<stem>rc` or `.<stem>rc.json`. It holds no declaration and is read for its strings alone.

### Strings in configuration

In a configuration file and in a JSON configuration file, every string literal and every template literal with no substitution, at any depth, is read against the `package.json` of the file's directory and against the file's own directory:

- A string equal to the name of a dependency that manifest declares, or to that name followed by `/` and a subpath, is a use of the dependency.
- A string that names, read against the file's directory, a source file of the program, directly or with one of the extensions the program's module resolution tries, roots that file, whether or not it starts with `./` or `../`. A string that starts with `/` or holds one of the glob characters `*`, `?`, `[` and `{` names no file.

A JSON object member's name is not read as a string. A string at a selection key of an applied convention row roots no file, as the convention rows below state, and a string in the configuration of a tool no applied row describes is read by this rule alone.

### Script entries

Each value of the `scripts` member of a `package.json` the analysis reads, the target's and each workspace member's, is split at white space and at the shell operators `&&`, `||`, `;` and `|`, and each token, with one pair of enclosing quotes removed, is read against the manifest's directory. A token that names a file of the program, directly or through the emit mappings that read an output file back to its source, roots that file.

### Workflow steps

A workflow file is a file whose name ends with `.yml` or `.yaml` in the directory `.github/workflows` of the target root. It is read as text, line by line, with no YAML parsed. A line whose text after its indentation, and after one sequence marker, a hyphen and a space, starts with `run:` holds a run command. The command is the rest of that line, with its surrounding white space and one pair of enclosing quotes removed. Where that rest is a block scalar indicator, `|` or `>` with an optional `+` or `-` after it, the command is instead each following line indented further than the column where `run:` starts, up to the first non-blank line that is not. Each line of a command is split as a script entry is, at white space and at the shell operators `&&`, `||`, `;` and `|`, with one pair of enclosing quotes removed from each token, and a `#` is read as any other character. A token that names a source file of the program by its whole path relative to the target root, with or without a leading `./`, roots that file, whatever directory the step runs in. No extension is tried and no emit mapping is read. A token that holds `$`, `{` or one of the glob characters `*`, `?` and `[` names no file, because a computed command is not read.

### Manifest entries

Each entry point a `package.json` the analysis reads names, its `main`, `module`, `types` and `bin` and every target of its `exports`, is read back to a source file of the program: the file the target names where the program holds it, else the file the emit mappings of the workspace rule above read it back to. A target that neither reads back to a source file is read back by name to the files the configuration-file, script-entry and HTML-entry rules of this section root. Its name is its path relative to the manifest's directory below its first directory, or the whole path where it names no directory, without its output extension, being `.d.ts`, `.d.mts`, `.d.cts`, `.js`, `.mjs`, `.cjs` or `.jsx`. A rooted file whose path relative to the manifest's directory, without its source extension, ends with that name at a directory boundary is the entry point, so `dist/cli/main.js` reads back to a rooted `src/cli/main.ts`. Every file that matches is the entry point, for the roots and for a library's published API alike, and a target that reads back to no file roots nothing.

### Release tags

In a library, an exported TypeScript declaration whose documentation comment holds the release tag `@public`, `@beta` or `@alpha` is published API, as a declaration a manifest entry reaches is, and so is each public member of a type it declares. Its documentation comment is the last `/** */` comment before it with only white space between the two. A tag is written as `@` and its name, after white space or the comment's opening and before white space or the comment's end. Such a declaration is live under reachability alone, as the published API is, and a finding about it carries the reachability class the confidence rule below gives the published API. That class is `possible` when the run holds no consumer information, `probable` when a declared consumer did not load, and `certain` when every declared consumer loads, so a tagged declaration no loaded consumer uses is reported at `certain`. In an application the tags mark nothing, because an application has no published API.

### HTML entry files

A file whose name ends with `.html`, below the target root and in no `node_modules` directory, is an HTML entry file, read as text as a component file is, with no markup parsed. A `<script` start tag whose `type` attribute is `module` begins a module script, and one inside an HTML comment begins one too, because no markup is parsed. A module script with a `src` attribute roots the file `src` names. One without roots each file that a specifier starting with `/`, `./` or `../` names, of an import or a re-export declaration in its content up to the next `</script>` end tag. An attribute is written `name="value"`, `name='value'` or `name=value`, and its name compares without regard to case. A value or a specifier that starts with `//` or with a scheme and a colon, `https:` among them, names no file. One that starts with a single `/` is read against the directory of the nearest `package.json` at or above the HTML file, and any other against the HTML file's own directory. Either resolves as a relative specifier of a configuration file does, and one that names no source file of the program roots nothing. A file a module script roots is a root as an entry of `ts.entry_files` is.

### Type-query aliases

An ambient global declaration in a declaration file whose type is `typeof import(<string>)[<string>]`, or `typeof import(<string>).<name>`, is an alias of the declaration that names the module the first string names exports under the second string or the name. A reference to the global is a reference to that declaration and to every link of the alias chain that reaches it, and the type query in the global's own declaration is not a reference. No finding is reported about the global declaration itself.

### Convention rows

An analyzer may carry a table of convention rows, each the data of one framework's file-system conventions. A row has a name, an enabling package, a version range in the semantic-versioning range syntax, the globs of its entry files, the globs of the files it excludes, the directories its framework generates, the configuration properties that move a directory those globs name, each with the configuration files the property is read from and, for a property that is an option of a call, the module and the exported name of the function called, the configuration properties whose value names a package by a short name, each with the configuration files it is read from and the package name the value stands for, written with `{}` where the value goes, the selection keys, the configuration properties whose value only selects files to test, to mutate, to cover or to ignore, each with the configuration files it is read from, and the manifest keys, the members of a `package.json` its tool reads its configuration from. The table is part of the analyzer, versioned with it, and no configuration key adds a row.

A row applies when a `package.json` the analysis reads declares the enabling package as a dependency, a development dependency, a peer dependency or an optional dependency, and the version the installed package's own `package.json` names, found from that manifest's directory as the compiler resolves a package, is in the row's range. An enabling package declared as a dependency or a development dependency whose installed manifest the analysis cannot find is the setup failure `missing-module`. An enabling package declared only as a peer dependency or an optional dependency whose installed manifest the analysis cannot find applies no row and raises no setup failure. An applied row's globs are matched against the directory of the manifest that declared the package: every file an entry glob matches and no exclude glob matches is a root, as an entry of `ts.entry_files` is, and every file below a directory the row names as generated, read against the same directory, is a generated file, whose declarations the `generated-file` class of [`exemptions.json`](../exemptions.json) retains.

A property that moves a directory is read from the row's configuration file without running it, in the objects the row reads there. Where the property is not an option of a call, the object is the file's default export, in each of its forms: the expression `export default` writes, the value assigned to `module.exports`, the binding an `export { name as default }` specifier names, and the document of a JSON configuration file. A default export that names a top-level `const`, `let` or `var` binding is read through to that binding's initializer, and one that is a call is read through to the call's first argument, until an expression that is neither. Where the property is an option of a call, the objects are the first arguments of every call in the file to the row's function, imported from the row's module by its exported name under any local name, or called through a namespace import of that module; an argument that names a top-level binding is read through to its initializer, and no further call is followed. In a file that declares no binding named `require`, a top-level `const`, `let` or `var` declaration whose initializer is a call of `require` with the row's module as its one argument, written as a string literal, binds as an import of that module does. An object binding pattern binds each exported name it lists under its local name, as a named import does, and a binding that is a name binds a namespace import. Parentheses, `as`, `satisfies` and the non-null assertion are read through wherever an expression is. A call with no argument, and a file with no object to read, set nothing.

The property is a path of keys through nested object literals, each key matching a property whose name is an identifier, a string literal or a template literal with no substitution, or a computed name whose expression is a string literal or a template literal with no substitution. Where the value at the end of the path is a string literal or a template literal with no substitution, the globs read each directory so set; where no object the row reads sets the property, the globs read the default directory. The row is the setup failure `convention-not-literal` where the value at the end of the path is anything else, a template literal with a substitution, a concatenation, a call and a name among them; where a value along the path is not written as an object literal, a name bound to an object literal among them, because a key's value is not read through a declaration; where the object the row reads is not written as an object literal, a default export that is a function or a class among them; and where the object the row reads or an object along the path holds a spread, or a computed name whose expression is not a string literal, a numeric literal or a template literal with no substitution, because either may set any key. An object the row does not read, the options of another function in the same file among them, sets nothing and raises no failure.

A property that names a package by a short name is read from an applied row's configuration files as a property that moves a directory is, and a string value at the end of its path, or a string element of an array value there, stands for the package name the row writes with that string in place of `{}`. A declared dependency of that name is used. Where the value is not a literal, every declared dependency whose name the row's package name can produce with some value in place of `{}` is used, and the row raises no setup failure for the property. A string value equal to a declared dependency's own name is a use under the strings rule above whatever the row says.

A selection key is read from an applied row's configuration files as a property that moves a directory is. A string value at the end of its path, or a string element of an array value there, roots no file under the strings rule above, because the tool reads a file it selects only when another key runs or loads that file. A key that runs or loads a file is no selection key, so a string it holds roots the file it names. A selection key whose value is not a literal raises no setup failure, and every string the file holds elsewhere is read under the strings rule.

A manifest key is read from the `package.json` that declared the row's enabling package. Every string at any depth of that member's value, a JSON object member's name excepted, that equals the name of a dependency the manifest declares, or that name followed by `/` and a subpath, is a use of the dependency. A string under a member that no applied row names as a manifest key is no use of a dependency under this rule.

The configuration's own keys win. A row `ts.disabled_conventions` names does not apply, adds no root and raises no setup failure, and the entries of `ts.entry_files` are roots whether a row applies or not. A row only adds roots, uses and retentions. The report lists each row it applied in `conventions_applied`.

## Confidence

A finding's reachability class states what the analysis can see of its subject's users. A subject of a library's published API, a public member of a type the published API names included, is `certain` when every declared consumer loads, `probable` when a declared consumer did not load, and `possible` when the run holds no consumer information. A library's internals, which outside programs cannot name, and every subject of an application are `certain`, except a declaration of test-support code that test code references and `DS1005` does not report, which is `possible` in every target kind. A finding's confidence is its reachability class capped by its kind's `max_class`. A finding about a member of a dead component, a root member included, is capped as well by the lowest such value among the component's root members, so every finding of one component carries one confidence and the minimum withholds or reports the component whole. A test of dead code whose component holds a published declaration therefore carries no higher confidence than that declaration, whatever reachability class the test itself has. `analysis.min_confidence` defaults to `probable`, so a run withholds the `DS1004` and `DS1201` findings about test-support code that test code references, a run over a library with no declared consumer withholds the findings about its published API as well, and every other finding is reported; the dial is the one mechanism that withholds a published API, and no kind's default depends on the target kind. The report's `totals.withheld` counts, per confidence, the findings the minimum withheld: the findings a run with `analysis.min_confidence` set to `possible` would report at that confidence that this run does not. The text and SARIF outputs name the counts in one line with the setting that shows them, as [`text-line.md`](text-line.md) states.

## Type errors

A type error the compiler reports in source the program holds does not end the run. The function, method or file-level statement whose source holds the error's position is not evaluated: nothing is reported about it or about any part of it, every reference in it the compiler resolves still counts, and every declaration an expression of it that does not resolve could reach is retained, so the skip can only withhold a finding. A diagnostic the compiler marks as reporting unnecessary code is not a type error for this rule, in any file. Each type error that skipped something is listed in the report's `type_error_skips` with its file, its line and the compiler's message, printed on standard error, and rendered as a warning annotation by the `github` format; the exit code follows the findings.

A type error in a dependency's declarations, outside the program, is not the program's and skips nothing.

## Unanswered questions

A question the analysis asks its type checker that the checker fails to answer is never read as an answer. Every declaration the answer could have made live is held: no finding is reported about it, every liveness relation treats it as live, and a declaration that reads a held binding by name is held too. Each configuration in which at least one question went unanswered is listed in the report's `unanswered_questions` with the number of questions and of declarations held.

## Setup failures

A setup failure is a file or a component the analysis needs and the project does not provide. In a configuration the configuration document declares, it ends the run with exit code 3 before any finding list exists, because every missing piece hides real uses and a partial run would report live code as dead. A configuration the analysis derived is dropped instead, as a derived configuration it cannot build is: it is listed in the report's `configurations_not_built` with the failure's line as its `error`, and the run analyzes the configurations left. When the analysis drops every configuration it derived, no matrix is left to analyze, and a setup failure among them ends the run as a declared configuration's does. For each failure that ends the run, the run prints one line on standard error that starts with `setup failure:`, a space, the class, a colon and a space, and names what is missing and the fix:

- `setup failure: missing-module`: an import names a module the project expects to exist and nothing provides it. A module the project expects is a module of the target's own module or a path its configuration maps, a declared dependency, a workspace member, and a module under a directory the project's ignore rules leave to a generator or a build. The fix names the import, the file that writes it, and the generator, the build or the install to run.
- `setup failure: incomplete-module-sum`: the Go module sum file lacks a checksum the build needs. The fix is `go mod tidy` in the module that requires it.
- `setup failure: test-build-tag`: Go test files build under no configuration of the run, because a build constraint they carry is satisfied by none. The fix names the exact entry of `analysis.configurations` that builds them.
- `setup failure: missing-consumer`: a declared consumer is absent from the path the scope names, or its own dependencies are not installed. The fix names the consumer, the path and the install.
- `setup failure: workspace-member-without-source`: a workspace member import reads back to no source file. The fix names the member, the subpath, the importing file and the targets the manifest names, and asks for a build of the member or an output and root directory that map the target to its source.
- `setup failure: convention-not-literal`: an applied convention row's directory property is not a literal. The fix names the configuration file and the property, and the alternative of disabling the row in `ts.disabled_conventions` and naming the files in `ts.entry_files`.

A configuration the invocation or the configuration document names that cannot be read ends the run with exit code 3 as well, and so does a run that needs more memory than the machine makes available, which prints the line `memory_exhaustion` in [`exit-codes.json`](../exit-codes.json) states.

## Notes

A note is a hint about the run's setup that the analysis cannot decide. It is no finding: the findings beside it are reported as they would be without it, and it fails no run.

- `published-package`: a Go package of an application, not a `main` package and not under an `internal` directory, that no file of another package of the target imports. Outside programs may import such a package, and only the user knows whether they do; the note names the package's directory and `roots.patterns`, the key that roots its published declarations.
