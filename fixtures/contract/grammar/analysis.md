# The analysis

This page states the rules every analyzer applies to decide what the program is, which of it is test code, what is live without a reference, what a type error withholds, which failures end a run and which hints a report carries. A rule here holds for both languages unless it names one. The vocabulary the rules report in is [`kinds.json`](../kinds.json), the configuration keys they read are [`config.schema.json`](../config.schema.json), the report members they fill are [`report.schema.json`](../report.schema.json) and the exit codes they end with are [`exit-codes.json`](../exit-codes.json).

Every rule on this page that adds a root, a use or a retention only ever makes a subject live: no such rule turns a live subject dead, and none raises a finding's severity or confidence. A file such a rule makes live is judged member by member: the file is no longer reported, and each of its declarations is reported or held as its own references decide, so the one finding about the file may give way to findings about the declarations it holds. The rules that end a run end it before any finding list exists.

## The target kind

The configuration's `target.kind` names one kind for the whole target, or one kind for each language. Every rule of the Contract that reads the target kind, on this page, in [`kinds.json`](../kinds.json), in [`exemptions.json`](../exemptions.json) and in the configuration keys, reads for a declaration the kind of the declaration's language: a rule stated for a library holds for a declaration whose language has the kind `library`, and a rule stated for an application for one whose language has the kind `application`. So in a target whose Go code is an application and whose TypeScript code is a library, the published API is the TypeScript code's alone. The published API as a root, the reachability class of its findings and the minimum confidence that withholds them, `consumers.complete`, the published-package note and the conversions an outside program writes are among those rules, and the rule is not limited to them. An analysis reads the member of its own language, and an analyzer that claims two languages applies each member to its own language's declarations. A cross-language edge reads no kind, because each of its sides is decided by the analysis of that side's language. A report states the kind of the languages it covers, as [`report.schema.json`](../report.schema.json) states.

## The program

The program is the source the analysis holds for the target and its declared consumers under each configuration of the run. A run that holds no program, a target with no source file of its language or a configuration that names no file, ends with exit code 3.

Where a configuration sets `baseUrl`, itself or through a configuration it extends, the analysis resolves its imports as the compilers before version 7 resolve them, which read `baseUrl` and version 7 does not: each `paths` target is read against that `baseUrl`, and a specifier no other pattern of `paths` maps is looked up below it, as a `*` pattern mapping to `<baseUrl>/*` would, which the configuration's own `*` pattern replaces.

### The derived Go matrix

A Go matrix that the configuration document does not declare is derived from the build constraints of every Go file under the target root, a test file's as much as any other file's, except a file whose constraint holds only when `ignore` is set, plus the host platform. So a tag only test files name, `race` among them, derives a configuration exactly as a tag any other file names does, and a derived configuration that does not build is dropped, as the setup failures below state. A test file that no configuration of the matrix builds is outside the run, as any other file no configuration builds is, and under a matrix the configuration declares complete it is reported under `DS1501`.

The `ignore` tag is the toolchain's convention for a file kept out of ordinary package builds unless a configuration explicitly satisfies the tag, and no derived configuration sets it. A file whose build constraint holds only when `ignore` is set, whatever else the constraint names, and that no configuration of the run builds, is outside the analysis: no finding, `DS1501` included under a complete matrix, no warning and no listed type error is about it or about a declaration it holds, and no reference it writes counts. Where its package clause is `main`, such a file is a program run by naming the file, so each declaration of the target that it names is a root. Its names resolve as they do when the toolchain builds that file alone under the host platform, and a name that does not resolve roots nothing. A configuration the configuration document declares may set `ignore`, and a file such a configuration builds is analyzed in it as any file that configuration builds is.

A derived configuration in which a package of the target has a type error that another configuration of the matrix type-checks without one holds no root for that package's type errors and lists none of them in `type_error_skips`: the configurations that build the package judge it. A package no configuration type-checks keeps the type-error rule in every configuration.

### The Go modules of a target

The Go program of a target is every Go module the target holds. A target whose root holds a `go.mod` file is that module and every module below it that the workspace file listing the target lists, and any other module rooted below it is a module of its own, which the target's build reads as a dependency or not at all. A target a `go.mod` file above it governs is a directory of that module, and no module below it is a module of the target. A target whose root holds none and that no `go.mod` file above it governs is every module rooted below it: each directory holding a `go.mod` file, searched in no `vendor`, `testdata` or `node_modules` directory and in no directory whose name starts with `.` or `_`. Each module loads from its own directory with its own module file and its own build list, and one report covers them all: every position is relative to the target root, a reference from one module of the target to a declaration of another counts where the first builds the second from the second's directory, through a `replace` directive or a workspace, and a directive of a module file is reported against that file, scoped by its module path. A declaration of a copy outside the target that shares a module's path, a module cache entry among them, is no declaration of the target. The derived Go matrix reads the files of every module. The report's target identity is the module path of the module rooted at the target root, else the scope document's `target.id`, else the module path of the first module in directory order.

A module that a `go.work` file at or above its directory lists among its `use` directives loads through that workspace, as `go build` run in that directory does, and every other module the workspace lists outside the target is a dependency of it, of which nothing is reported. A module the nearest workspace file does not list loads with no workspace, whatever the environment sets.

A module the search below a target root that holds no `go.mod` file finds, and that does not load, a setup failure or a load error, is dropped: the run analyzes the modules left and the report carries a `module-not-loaded` note naming its directory. When every module is dropped the first failure ends the run as any setup failure does. A module the target is, and a module its workspace file lists, are named by the target and end the run when they do not load.

Below a target root that holds a `go.mod` file, a module of its own that requires a module of the target and replaces it with that module's directory builds against the target's tree, so the run loads it as a consumer: its references count as a declared consumer's do, nothing of it is reported, and it is no declared consumer, so it changes no reachability class and the report's `consumers` does not name it. One that does not load is dropped with a `module-not-loaded` note. A module that requires a published version of the target is no consumer of this tree. A module that builds against the target's tree below a directory whose name starts with an underscore is a consumer all the same. A package of a module of the target below such a directory, an example program's among them, is one no pattern ending in `/...` matches, so no build of the module compiles it, and the run loads it as a consumer of its module in the same way: its references count, nothing of it is reported, and one whose imports do not resolve counts nothing.

A module the workspace listing the target lists outside it, which a report names only from a run directory that holds it, still counts its references when the report cannot name it: one whose `go.mod` requires a module of the target is loaded through the workspace as a module below the target that builds against the target's tree is, and the report's `consumers` does not name it.

A module of the target that a dropped module's `go.mod` requires has it as a consumer the run did not analyze, so every exported declaration of an importable package of that module has the reachability class `possible`; a module whose dropped neighbour's `go.mod` cannot be read is treated as required.

Every position a setup failure line names is relative to the target root, a module's below it included.

### Component files

A derived TypeScript matrix holds the test files the test runner compiles. A file `ts.test_files` names that no derived configuration's file list holds joins the configuration of the nearest compiler configuration file at or above its directory that the matrix holds, `tsconfig.json` first where one directory holds several and the others in bytewise order of their names, as a file that configuration's file list names, because the test runner compiles the file with those options. It joins only where the nearest `package.json` at or above its directory is the nearest `package.json` at or above that compiler configuration file's directory, or neither has one, because a file below a manifest the configuration does not share belongs to another package, whose own test runner compiles it. A file with no such configuration at or above it, or whose nearest `package.json` that configuration does not share, joins none. A matrix the configuration document declares is the maintainer's, and no file joins it this way.

A derived TypeScript matrix holds each compiler configuration under the target root and each configuration below the target root that one of them references, transitively, as the compiler reads the reference: a path that names no `.json` file names the `tsconfig.json` in that directory. A configuration below the target root that a declared configuration references and the configuration document does not declare ends the run, because the compiler builds a referenced project's sources into the program that references it without reporting their diagnostics. A referenced configuration outside the target root is an outside project: the compiler builds its sources into the referencing program as declarations outside the analysis, so a reference into them counts as a reference to a dependency's declaration does, and nothing about them is reported.

A file whose name ends with an extension `ts.component_extensions` lists is a component file. A component file is in a project's program when the project's file list names it or an import of the program resolves to it, and an import of a component file resolves to that file. The analysis reads a component file as markup holding script blocks, and it parses no markup:

- A `<script>` element whose start tag begins a line at the top level of the file is a block. Its content, up to the matching `</script>` end tag, is source of the language its `lang` attribute names: `ts` and `tsx` are TypeScript, and a block with no `lang`, or with `js` or `jsx`, is JavaScript.
- A comment, which holds no block, ends as the parser of the file's framework ends it. In a file whose extension is `.svelte` it ends at the first `-->` after its opening `<!--`. In any other component file it ends at the first `-->` or `--!>` that starts after its opening `<!`, the opening dashes counted, so `<!-->` and `<!--->` are whole comments. A `{` that no `}` closes inside a start tag hides no later block. In a `.vue` file it is a character of an attribute name or value, and the tag ends at the next `>`. In any other component file the braced value ends at the next `>` or before a `<script` start tag that begins a line, whichever comes first. Either way, a start tag holding such a brace ends before a `<script` start tag that begins a line.
- A file whose first line is `---` holds a frontmatter block: the lines after it up to the next line that is `---` are a TypeScript block.
- A `<script>` element with a `src` attribute, in its self-closing form or with an end tag, is a namespace import of the file `src` names, positioned at the attribute. It references every export of that file, as a retained namespace import binding does.
- The blocks of one file are one module, read in file order, of the strongest language any block names, in the order TSX, TypeScript, JSX, JavaScript. A file that holds no block is an empty module.
- A `<script` start tag that begins a line and is not read as a block, or that begins a line inside a block, is printed as a warning on standard error naming the file and the line, and the file is analyzed without it.

Every top-level binding of a component file's module is retained while the file is live, because the markup may use it: a declaration, and an import binding, which is resolved to the declaration it names, a namespace import to the module it names, and a named or default import to the export it names, followed along the export's re-exports. Where an import binding resolves to a module, as a namespace import does and as a named or default import of `export * as ns from` or `export * as default from` does, every export of that module counts as used, because the markup may read any of them and the analysis parses no markup. No finding is reported about a retained binding, `DS1104` included. Everything the module references counts as a use. The markup of a live component file is template text for the `template-field` exemption of [`exemptions.json`](../exemptions.json), so a member whose name the markup holds is retained by that class. A type error in a block is a type error under the rule below.

### Workspace packages

A TypeScript workspace is declared by the `packages` sequence of a `pnpm-workspace.yaml` file, or by the `workspaces` member of a `package.json`, an array of globs or an object whose `packages` member is one. The analysis searches for the declaration from the target root upward to the first directory holding one, and no further than the root of the repository that holds the target. A member is a directory the globs name, minus the globs a `!` negates and never under a `node_modules` directory, that holds a `package.json` with a `name`; the directory holding the declaration is a member too.

An import whose package name is a member's resolves to the member's source, so a workspace is analyzed with no build and no path mapping:

1. Where the package manager linked the importing directory to another package of that name, and that package is not the member, the import keeps the resolution the compiler gives it, and so does an import from outside the member that the member's name does not link.
2. Otherwise, where the compiler's own resolution reaches a source file inside the member, that file stands. A declaration file stands only when no configuration of the member writes its output where the file is.
3. Otherwise the member's manifest decides: the `exports` entry the import's subpath selects, the exact key first and then the longest pattern, its targets tried in condition order; with no `exports`, `types`, `typings`, `main` and `module` for the package itself, or the subpath below the member's directory. Each target is read back to its source through the member's emit mappings: each compiler configuration of the member maps its output directory and its declaration directory to its root directory, or, with no root directory, to the configuration's own directory and then to the common directory of its input files, and an output file maps to the source file of the same name with the source extension the output extension stands for. A target that is an existing file and neither a TypeScript source nor compiler output, a stylesheet or an image, is no module with a source: the import keeps the resolution the compiler gives it, and a failure to resolve it is a type error of the importing statement, not a `workspace-member-without-source`.
4. An import no candidate reads back to a source file is the setup failure `workspace-member-without-source` below.

A file the `.gitignore` files at and below the workspace's root ignore, as git reads them, is output a build left in the tree, not a file the member's sources or an install wrote. Where the compiler's resolution, or a target, reaches one inside a member, rule 2 does not keep it, and it reads back, after the emit mappings, to the source its path mirrors: its path below one of its directories inside the member, the deepest first, read below the member's own directory with the source extension its output extension stands for, a source file no `.gitignore` ignores. This holds for a member no compiler configuration builds as well. An ignored file whose path mirrors no source keeps the resolution the compiler gives it.

An import is read from the package of its file: the member that holds the file, or, where no member does, the package of the nearest `package.json` at or above the file below the workspace's root, so a package below the target that no workspace lists and whose manifest depends on a member, an example among them, imports the member as a member does and is a loaded consumer of it. A reference from every program that holds a member's file counts, so a declaration a sibling member uses is live. A finding about a member's file is reported only from a configuration that owns the file, one whose own file list names it; a configuration that holds the file only because an import reached it contributes references to it and no verdict about it. A member's manifest entries are roots as the target's own are. A member whose manifest does not mark it private is a published package: its manifest entries, read back to their source, are its published API, so in an application target it is a library inside the target and the confidence rule below gives its published API the class a library's published API carries.

### Nested packages

The manifests the analysis reads are the target's `package.json`, each workspace member's, and each nested package's. A nested package is a directory below the target root, in no `node_modules` directory, that holds a `package.json` and lies at or above a source file of the program or a compiler configuration file of the run. A `package.json` above no such file governs nothing the run holds, the manifest of a test fixture or of an example that every compiler configuration leaves out among them, so it is not read. Every rule of this page that reads a manifest the analysis reads reads each of them against its own directory: script entries, manifest entries, configuration files, the application of convention rows, and the dependencies `DS1601` in [`kinds.json`](../kinds.json) judges. So, under the same configuration document, a run at the target root applies to a nested package's files and manifest every row, root and use that a run whose target is that package applies. The root run adds what only the root holds: a workflow step, an HTML entry file outside the package, a reference from a file outside it, and a row an enclosing nested package's manifest applies, which matches the files of a package nested inside it too. A configuration document a nested package holds is not read by a run at the root, because a run reads one configuration document, so the two runs differ as their documents do.

## Test code

Test code is the test files and the test-support code. A test file is a Go file whose name ends with `_test.go`, and a TypeScript file `ts.test_files` names or an applied convention row's test-file property names. A test is a declaration of a test file, a test function the test runner calls among them. Test-support code is the code only tests reach: the largest set of Go packages and TypeScript files, none of them a test file and each carrying test evidence of its own language, such that a test reaches each member, no member holds a root, and every import of a member and every reference to a declaration of a member from outside it is written in a test file or in another member. A TypeScript file is a member only where it carries test evidence of its own: an import of a test runner or a test library, being the runner of each convention row that names test files, `node:test`, `@playwright/test` and every package of the `@testing-library` scope, or package imports, one or more, every one of them a package that the nearest manifest at or above the file declaring it declares under `devDependencies` alone and that no file outside the test files and the files only tests reach imports, a Node.js built-in module, bare or under the `node:` scheme, being no package. A TypeScript file only tests reach that carries no such evidence is production code, so a declaration of it only tests reference is reported under `DS1004`. A reference here is a name that resolves to the declaration, so a call through an interface method or a function value references no implementation. A Go package is here its files other than test files, so a reference from its own test files is from outside it. A test reaches a package or a file through a chain of imports and references that starts at the test, whatever members the chain passes through. So every chain that reaches test-support code starts at a test, however many members lie between: a package only another member imports is test-support code, and so is a package whose only users are its own test files. Production code a test calls stays production code, because a chain from production code or from a root reaches it too. A Go package carries test evidence when one of its files other than its test files imports the standard library's `testing` package, and then each of those files is test-support code where the package is a member. Code with no test evidence of its own stays production code however few chains reach it, so a package only tests reach that carries none is production code a test uses: a declaration of it that only test code references is reported under `DS1004`, one nothing references under the unused code its visibility selects, and a reference from it is a production reference. Evidence is a property of the code, never of its file name or its directory, so no name or location makes code test-support code or keeps it out. A Go `init` function and a blank declaration run because their package is loaded, so neither is a root for this rule. A Go package or a TypeScript file a library's published API reaches is not test-support code, because outside programs may import it. The analysis classifies code by the chains that reach it and does not judge whether a test is a good one, so a test that reaches no production code is not reported for that.

Test code is judged with the tests:

- A reference from test code is a test reference, and a production sweep, which counts no test reference, judges no declaration of test code.
- A test function the test runner calls is a root. In Go it is a test, a benchmark, an example or a fuzz test of a test file, or `TestMain`. In TypeScript the runner loads a test file and calls what its top level registers, so the file's top level and every function its export table names are roots, and so is every export of a file below a `__mocks__` directory, which the runner puts in place of the module it mocks. Any other export of a test file is no root: it is judged as a declaration of a test file that is no root, so one nothing references is reported, and one only its own file references is reported under `DS1104`. Such a root is reported only under `DS1005`. A Go `init` function and a blank declaration of a test file are roots as they are in production code, because they run when the test binary loads their package. Neither is judged under `DS1005`.
- A declaration of a test file that is no root is reported under `DS1005` where that kind's rule holds for it. Otherwise it is reported when nothing references it, under the code a production declaration with the same shape carries: `DS1201` for an interface and the unused code its visibility selects otherwise. A declaration of a test file that only reported declarations of test files reference falls with them, in their dead component. A production declaration such an unreferenced declaration references stays out of that component: its own references decide its code and its component, and the reference counts as a test reference.
- A declaration of test-support code is test code: a reference from test code keeps it live under both liveness relations, so it is reported under `DS1001`, `DS1002`, `DS1003` or `DS1201`, the code a production declaration nothing references carries, at `certain` only when nothing references it, and under `DS1005` where a declaration of a test file would be. An export of it that test code references and only its own file references is reported under `DS1104`, as such an export of a test file is, and its reachability class is not lowered for the test references that keep it live. A finding about one nothing references belongs to the dead component of the declarations it reaches. A declaration of test-support code that a test referencing a live target symbol also references counts as a live target symbol of every test that references it, so such a test is no test of dead code, and test-support code is no other target symbol when `DS1005` judges a test or a declaration of test-support code.
- A part of a declaration of test code, a parameter, a receiver, a result, a statement, a store or a case, is reported only while the declaration is live in the run that counts test references. A TypeScript part that no declaration holds, written in a file's top-level statements or in a function they pass or hold, belongs to the file and is judged while the file is live, so the parts of the callbacks a test file registers are judged in the run that counts test references, as the body of a Go test function is. A declaration of test code nothing live references is not judged, so none of its parts is reported, and a declaration of test code reported under `DS1005` or as unreferenced is reported whole.

A file the analysis classified as test-support code is counted in the report's `test_file_rules` under the rule `test-support`.

## Uses through memory layout

In Go, a conversion of a pointer to `unsafe.Pointer`, or of an `unsafe.Pointer` to a pointer type, reads and writes every field the pointed-to type lays out, recorded at the conversion: every field of it where it is a struct type, every field of its element type where it is an array type, and so on through every field of a struct type and every element of an array type it holds, at any depth. A field or an element holding a pointer, a slice, a map, a channel, a function or an interface is itself read and written, and the use goes no further into the storage it refers to, which the pointed-to type does not lay out. Where the pointed-to type is a type parameter, or a struct or array type that holds one at any depth, the conversion has the same use of each type argument that type parameter takes in an instantiation the program holds, an instantiation made through another generic declaration's own type parameters included, because the instantiated type is the one the conversion lays out. A struct type that declares a field of type `structs.HostLayout` has the same use of every field it lays out, recorded at that field, because its layout is fixed for code outside the program. Code that reads memory through either names no field, so no field such a use reaches is reported under `DS1003` or `DS1301`.

## Conversions an outside program writes

In a Go library, a program outside the analysis that imports the published API can hand a value it holds to any published parameter the value's type fits. A published function is an exported function of a package of the published API, an exported method selectable on a value of a type an outside program can hold, a method promoted through an embedded field of any visibility included, and an exported method of an interface type the published API reaches, as the confidence rule below states what the published API reaches, and a published parameter is a parameter of a published function.

An outside program can hold a value of each exported type a package of the published API declares, and of each type the published API hands it: the type of a result of a published function, of an exported variable and of an exported constant of a package of the published API, and of each exported field selectable on a value of a type it can hold, a field promoted through an embedded field of any visibility included, and the type of a parameter of a function type that a published parameter has and of a parameter of a method of an interface type the published API reaches, because the published code calls such a function or method with values of its own. It can hold as well the element, key and result types of a pointer, slice, array, map, channel or function type it can hold, and so on until no further type joins. The analysis counts no value an outside program obtains only through type inference over a published function value, through reflection or through `unsafe`, so a type the published API reaches only as the type of a parameter of a published function is not one it counts as held.

Where a published parameter's type is an interface type I, or its element type is one where the parameter is variadic, whichever package declares I and whether or not it is exported, the analysis records a site converting T to I, positioned at the parameter, for each type T the target declares that an outside program can hold, that is not an interface type and that implements I. For each type parameter of a published function, or of a generic type a package of the published API exports, whose constraint is an interface type I, however the declaration's parameters and fields spell the type parameter, the analysis records a site instantiating it with each such T that satisfies the constraint, positioned at the type parameter. Either site is a use by the declaration that declares the parameter or the type parameter, and the pair it records retains under the `interface-satisfaction` class of [`exemptions.json`](../exemptions.json) as any other pair does.

Two modelling bounds decide what implements I here, and each only retains more. A type T implements I where T or a pointer to T does, and the analysis does not model which of the two an outside program can form. A generic type implements I where some instantiation the type checker accepts could, which the analysis decides by matching each method of I to a method of the type of the same name with as many parameters and as many results, whatever their types.

The sites are recorded only while the published API's reachability class, as the confidence rule below gives it, is `possible` or `probable`. Where every declared consumer loads, that class is `certain`, the consumers are the outside programs the run knows, and the conversions they write are the run's own sites.

## References in Go

A constant specification of a parenthesized constant declaration that writes no expression list repeats the first expression list before it, and that list's type, as the language states. It therefore references each declaration that type and those expressions name, as the specification that writes them does. The reference is recorded at the specification's first name and held by each constant the specification declares.

A selector of a field of an unnamed struct type references the field at the same position of every identical unnamed struct type the target spells, because identical unnamed struct types are one type and each spelling declares its own field objects. A struct type a type declaration declares is not unnamed, and two struct type literals whose tags differ are not identical.

## References in TypeScript

### Module URLs

In a source file of the program, `new URL(<string>, import.meta.url)`, where `URL` names the global `URL`, and `import.meta.resolve(<string>)`, with the string a string literal or a template literal with no substitution that starts with `./` or `../`, name the file the string resolves to against the file's own directory, as a relative specifier of a configuration file resolves. A runtime starts that file as a module, a worker among them. The expression is an import of the file for its effects, written in the file that holds the expression: the file joins the import graph there, its top level is live while the holding file is, and no export of it is referenced. A file only test code loads this way is test-support code. A declaration of the target that merges into the global `URL`, such as an interface a `declare global` block declares, leaves it the global one, and a `URL` every declaration of which is in the target's files is not the global one.

A worker address, the first argument of `new Worker`, `new SharedWorker` or `navigator.serviceWorker.register`, written as a string literal or as a `URL` built as above, names the file the runtime starts as a module, and the call is an import of that file for its effects as the expression above is. A worker address is a URL reference: it is relative unless it starts with `/` or carries a scheme, so a bare name names the file beside the calling file as its `./` spelling does. A name the address is built with, `Worker`, `SharedWorker`, `navigator` or `URL`, is the platform's while any of its declarations is outside the target's files, so a declaration of the target that merges into it leaves it the platform's. The same bare-name reading holds for the `setupFiles` and `globalSetup` strings of a test-runner workspace file, which the runner resolves against the file's directory.

### Module namespace objects

A module namespace object is the binding of a namespace import, `import * as ns`, the value an `await` of a dynamic `import()` produces, the first parameter of the first callback passed to `then` on a dynamic `import()` call, and the binding of a `const`, `let` or `var` declaration whose initializer is one of these: a write to such a binding is a use of the object the second rule below reads as every export, so a binding the program reassigns references every export. A dynamic `import()` names a module when its argument is a string literal or a template literal with no substitution that the program's module resolution maps to a source file. An identifier that spells the binding's name without referring to it is no use: a property name an object literal, a class, an interface, a type literal or an enum declares, a JSX attribute's name, and a statement label with the `break` and `continue` that name it. A use of a namespace object references the module's exports by what it reads:

- A property access by name, `ns.name`, or by an index that is a string literal or a template literal with no substitution, references the export of that name, a re-export walked to the declaration it carries, and so does each property an object binding pattern destructures from the object.
- Any other use references every export of the module, because code the analysis does not follow may read any export through the object: the object or the `import()` call passed as an argument, returned, assigned to anything but such a binding, stored in a property or an element, spread, or indexed by any other expression, a `typeof` query of it included.
- A namespace object nothing uses references no export, and neither does a dynamic `import()` whose value is not used, being an expression statement, a `void` operand or an `await` whose result is not used: the call loads the module and nothing more.

### Module declarations

A `declare module` declaration whose name is a string literal, an augmentation of a module in a module file or an ambient module declaration in a script, is referenced by each import of the program that names its module. An import names the module when its specifier equals the declaration's name or when both resolve to the same source file. Where the declaration's name holds one `*`, an import names it when its specifier matches the name with the `*` standing for any run of characters. Such a wildcard declaration is how the compiler types the file a matching specifier names, so an import that names it by its pattern references it, and each member of it the import names, as a reference from production code, whether a test file or a production file writes the import. An import here is an import or a re-export declaration, a dynamic `import()` whose argument is a string literal or a template literal with no substitution, an `import x = require()` declaration and an import type, in any file of the program, the declaration's own file included. An import in a file that no configuration of the run holds names no module declaration, because no compiler run reads the declaration for that file. The reference is recorded at the import and held by the declaration that holds it, or by the file where the import is a top-level statement. An import that names a module declaration also references each member of it that the import names, the `default` member for a default import, the member of each name a named import or re-export lists and every exported member for a namespace import, whether or not the specifier also resolves to a source file, a component file among them. A module declaration is used as well where a declaration it holds is used, as a `declare global` block is, because it may augment a module no import of the target names, whose declarations code outside the analysis types values by. A module declaration no import names and none of whose declarations is used is reported whole under `DS1002`, and its members fall with it. While an import names it, each member of the declaration is judged as any other member of the program is, by its own references.

A `declare global` block, and every namespace nested in it, is used where a declaration it holds is used. An interface or a namespace declared at the top level of a file that is no module is a declaration of the global scope, as one such a block holds is, and the next sentence holds of it too. A member such a block merges into an interface the compiler's library declarations declare, `ImportMeta` or `Window` among them, is read where a read of that interface's member resolves to it, and it is judged by its own references as any member is.

### Overrides of outside classes

A method, an accessor or a property of a class of the target, static or not, that overrides a member of a class declared outside the target and its loaded consumers, in the compiler's library declarations or in a dependency, at any depth of the class's `extends` chain, is used by code outside the analysis that holds the instance or the class through that class: that code calls the method, reads the accessor or the property, and may write it. A class of the library declarations is an interface and a variable of one name, as `Error` and `Map` are, and a class whose chain reaches `Error` overrides its `toString` as well, which the runtime calls to print the error though the library's `Error` interface omits it. The member counts as read by the class that declares it, so it is live while that class is, it falls with the class when the class is dead, and it is never reported under a code of its own, as unused or as written and never read. A class keeps its place where its class declaration is: a declaration of the target that merges into a class declared outside the target, such as an interface a module augmentation declares, does not bring the class into the target.

### Overrides in the target's own classes

A use of a method, an accessor or a property through a value of a class type of the target, `this` inside the class's own members included, reaches the member it names and each member of a subclass of the target that overrides it, at any depth of the subclass's `extends` chain, because the runtime dispatches on the instance. An abstract member is referenced where such a use names it, and its overrides are live while it is.

### Members reached through types

A value reaches a position typed by a type when it initializes or is assigned to a declaration, a property, an element or a parameter that type annotates, when a function whose result type annotates returns it, and when a `satisfies` expression checks it against that type. An `as` expression is no such position. Where the value's type and the position's type differ, the value's type reaches the position's type, and a pair of types reaches as follows:

- An object type reaching an object type reads each member of the first that the second declares under the same name, because the compiler reads the member to check the assignment and code holding the position reads it through the position's type. A union or an intersection on either side is compared constituent by constituent, and a constituent of the value's type that is a constituent of the position's type reads nothing. A property of a mapped type over literal keys, `Record<"id", number>` among them, is a member the type declares under that name, although no declaration writes it, and no member of the value's type is that property.
- An array or a tuple reaching an array or a tuple reaches through its element types. A function type reaching a function type reaches through each pair of a call signature of the value and a call signature of the position, and a constructor type through each pair of construct signatures: each parameter type of the position's signature reaches the parameter type in the same place of the value's signature, and the value's result type reaches the position's result type. An overloaded function so reads each member any of its overloads' parameters declares, which reads more and never less than the overload the compiler resolves. An instantiation of a generic type reaching an instantiation of a generic type with as many type arguments reaches through its type arguments, each reaching the one in the same place, and an array or a tuple reaching an instantiation with one type argument reaches through its element type to that argument, as an array reaches `Iterable<T>`. The walk compares the arguments by place and not by the variance of the type parameters, which reads more and never less.
- A pair reaches once, so the walk ends when no pair joins.

A member read through a value whose type is a type parameter of a generic function reads the member of that name on each type a call of that function passes for the parameter, read off each parameter whose declared type holds the type parameter, directly or as a type argument, against the type the call passes there, because the value the read reads is the call's. A `for…of` statement and a spread element read the `[Symbol.iterator]` member of their operand's type, and a `for await…of` statement reads its `[Symbol.asyncIterator]` member and its `[Symbol.iterator]` member, which the statement falls back to, each at the operand, because the language calls them to iterate.

A property of an object literal writes the member of its contextual type that `DS1301` in [`kinds.json`](../kinds.json) names, and a read of that property through a value of the literal's own type, a declaration the literal initializes without an annotation included, reads that member.

A value whose type is declared outside the target and its loaded consumers, in the compiler's library declarations or in a dependency, that reaches a position typed by an object type of the target reads each member of the target's type that the value's type declares under the same name, because code outside the analysis holds the value and reads those members.

An object literal that is an argument of a call or a `new` expression whose callee has no implementation in the target reads each member of the type of the parameter it is checked against, as the call instantiates that type: each constituent's, for a union or an intersection, and the instantiated type where the declared one names a type parameter, so `items.push({ shown, hidden })` on an array of a target type reads both members. Where a property's value is itself an object literal, that literal's members are read in the same way, against the type of the member it initializes. A callee has no implementation in the target when the declaration of the signature the compiler resolves the call to has no body and nothing of the target stands for it. A function, a method, an arrow function, a function expression or a class of the target stands for the signature when it is the callee itself, or when it reaches, under the rule above, the declaration, the parameter or the property from which the callee's value is read. A value passed for a parameter reaches it only through a call that names the function declaring the parameter, so a function value passed through any other call leaves the callee with no implementation, which reads more. A class or an object literal of the target that implements an interface stands for that interface's method, call and construct signatures. The implementation of a target overload set stands for each of its overload signatures, and an override a target class declares stands for the abstract method it overrides. So each of these has no implementation in the target: a function declared in a declaration file or in an ambient context, a member of a `declare global` block's interface no target class or object implements, a function or a method that a dependency or the compiler's library declarations declare, and a call or construct signature of a type the target declares, held by a value no function or class of the target reaches, such as a value read off a global through an `as` expression. The rule reads an object literal written at the argument and nothing else: a value of the same type that a declaration holds and the call passes by name has its members written where its own literal is, and reads only what a read of it reads.

An `as` expression whose operand, through further `as` expressions and parentheses, has an object type no file of the target declares, and a `new` expression whose callee has no implementation in the target and whose signature's result is no type parameter, hand the target a value code outside it holds. Every member of each object type of the target that expression's type has is read, recorded at the expression. An `as` expression over a value of type `any` hands over nothing, so a decoded value asserted to a type of the target reads only what the target reads of it.

### Object spreads

A spread element `...x` of an object literal reads each member of the type of `x`, of each constituent where that type is a union or an intersection, that the spread copies. The runtime copies the value's own enumerable properties, so the spread reads each property and field of the type, a property an interface or a type literal declares included, and an accessor an interface or a type literal declares is read as a property is. It reads no method and no method signature, whoever declares it, because a spread copies a function and calls none, no accessor a class declares, which sits on the class's prototype, and no `#private` name, which is no property. A member is a class's method or accessor by its declaration, whatever type reaches it, so a mapped type over a class instance type, `Readonly<C>` among them, reads no accessor of `C` through a spread. The reads are recorded at the spread element and held by the declaration that holds it, or by the file where the literal is a top-level expression.

### Indexed-access types

An indexed-access type `T[K]` whose index type `K` is a literal type, a string literal type or a numeric literal type, or a union of literal types, references each member of `T` that one of those literals names, as a property access by that name does. Where `K` is a union mixing literal types with other types, its literal constituents are read so, and the others read nothing. Where `K` is a type parameter whose constraint is a literal type, a union of them or a type alias naming one, with no `keyof` in it, the access references each member of `T` the constraint's literals name, because the compiler accepts the access only while `T` declares each of them. The reference is recorded at the indexed-access type and held by the declaration that holds it.

An indexed-access type that names a type parameter is read after each type parameter it names is replaced by the type argument the reference or the call holding it fixes. A reference to a generic type alias, interface or class fixes the type arguments it writes. A call or a `new` expression fixes the type arguments of the signature the compiler resolves it to: the ones it writes, the ones the compiler infers from its arguments, and the ones bound by the instantiation of the generic declaration the callee is a member of, a dependency's declaration included. A `new` expression fixes them as a call does, its resolved signature being the construct signature of the class's constructor or of a construct signature type, and a class's parameters are its constructor's. A receiver's type argument is the one the instantiation of the generic declaration the callee is a member of has, whether the receiver's type is that instantiation or a class that extends it, directly or through other classes, `this` included. The callee is that resolved signature, whatever expression names it, a generic function an object literal's property holds included: a property access, a member of a namespace import, an alias, or a binding that an object binding pattern destructures from a value of an instantiated type. So `const { get } = createStore<Fields>()` followed by `get("title")` reads `Fields["title"]`, as `createStore<Fields>().get("title")` does. An inferred type argument is the type the compiler gives the argument, so a `const` binding, a member of an object an `as const` assertion fixes, an enum member and a template literal with no substitution each fix the literal type the compiler gives them. The substitution follows a generic alias's body, both branches of a conditional type and the members of a generic declaration. It reaches every indexed-access type held by the resolved signature's parameter and result types, through unions, intersections, array element types, type arguments, the members of an object type literal and the parameter and result types of a function type. So `Payloads[K]` inside an alias that a call fixing `K` to `"open"` instantiates references the member `open` of `Payloads`. A reference inside a mapped type `{ [K in U]: G<K> }` fixes the type parameter of `G` that its argument `K` names to `U`, so `{ [K in Kind]: Kinded<K> }` reads each member of `Payload` that `Payload[K]` in `Kinded` names for each literal of `Kind`.

The resolved signature has two kinds of `keyof` position. One is a type parameter of the signature whose constraint holds `keyof O`, read through generic aliases and conditional types as the substitution above reads them: the constraint itself, a constituent of a union or an intersection, or the checked type or a branch of a conditional type, so `K extends keyof O` and `K extends Extract<keyof O, string>` are both such positions. The other is a parameter whose declared type holds `keyof X` in the same way, where `X` is a type parameter of the signature or of the generic declaration the callee is a member of, so `clear(event?: keyof M)` on a member of `Bus<M>` is one, or any other type, the signature generic or not, so `clear(event: keyof Events)` is one too. A parameter that is optional is such a position as the same parameter written required is, its `undefined` constituent naming no member. Where the call fixes such a type parameter, or passes such a parameter an argument the compiler types, as a literal type or a union of literal types, each member of `O` that one of those literals names is referenced, as by the indexed access `O[K]`, whether or not the signature writes one. `O` is the type the resolved signature substitutes for the operand of `keyof`: the receiver's type argument where the operand is a type parameter of the generic declaration the callee is a member of, the call's own type argument where it is one of the signature's, and the operand itself where it is neither, as in `at<K extends keyof Fields>(key: K)`.

Where an index so read is a literal type or a union of literal types, the access references each member of the type that one of those literals names. The reference is recorded at the reference or the call that fixes the index and held by the declaration that holds it. A literal names the member the type declares under that name and nothing else. In a type that also declares an index signature, the declared members are read by the literals that name them, and a literal that names no declared member reads the signature, which is no member. An indexed-access type whose index is any other type references no member under this rule.

### Element access by a literal type

An element access expression `o[k]` whose index expression the compiler types as a literal type or a union of literal types references each member of the type of `o` that one of those literals names, as a property access by that name does: a read where the access is read, a write where it is the target of an assignment, and both for a compound assignment, an increment and a decrement. A string literal index is the case of one literal. An index typed `keyof T`, for a type `T` that declares no index signature, is the union of the names of `T`'s members. An index the compiler types as a type parameter is read as the type its constraint admits, because the function body serves every instantiation. An element access whose index the compiler types any other way references no member under this rule. Where the receiver's type is `any` or declares no string index signature, `reflective-lookup` in [`exemptions.json`](../exemptions.json) may retain a member a string literal names.

Where the index is a parameter of the function that encloses the access, the function's body never assigns that parameter, and every call of the function is one the target holds, the members the access references are decided at the function's calls instead. The body assigns the parameter where it is the target of an assignment, a destructuring assignment at any depth among them, of a compound assignment, an increment or a decrement, or of a `for…in` or `for…of` statement that declares no variable. Every call is one the target holds when the function is a function declaration, or a `const` variable whose initializer is an arrow function or a function expression, that is not exported, and every use of its name in its own file is the callee of a call, because a method may be called through a base class or an interface, an exported function from a program outside the target, and a function used as a value from a call the target cannot pair with it. At each call of the function the target holds, the access references each member of the type of `o` that the type the compiler gives the call's argument at that parameter names, under the rule above, recorded at the call, with the access's own kind of reference. A call that passes no argument there references the members the type of the parameter's initializer names, and nothing where the parameter has none. So `const at = (key: keyof Fields) => fields[key]`, called as `at("title")` and `at("body")`, reads `title` and `body` and no other member of `Fields`. Wherever any of these conditions fails, the access is read at the access by the rule above, through the type the compiler gives the index there, because a caller the target cannot pair with the function may pass any key that type admits. Where the type of `o` names a type parameter of the function, the access is read at each call after the substitution the call makes, as an indexed-access type is.

A string or number literal compared by `===`, `!==`, `==` or `!=`, or written as a `case` label of a `switch`, with an operand whose declaration's type holds `keyof X` references the member of `X` that the literal names, because the comparison selects the code that handles that key. The operand's declaration is read through an import or a re-export that names it, and the reference is recorded at the literal.

## Roots

A root is live without a reference. Beside the roots `roots.patterns` and `ts.entry_files` configure, the entry points a manifest names and a library's published API, the TypeScript analysis marks the roots below, and the Go analysis those of the subsections whose title names Go. A root that names a file roots the file's top level and everything its export table names, a re-export walked to the declaration it carries, and is live under both liveness relations, because a program the project runs loads it.

### Configuration files by name

A file in the directory of a `package.json` the analysis reads, below the target root and in no `node_modules` directory, is a configuration file when its name is `<stem>.config.<ext>` or `<stem>.<qualifier>.config.<ext>`, with `<ext>` one of `js`, `mjs`, `cjs`, `ts`, `mts` and `cts`, or `.<stem>rc.<ext>`, with `<ext>` one of `js`, `mjs` and `cjs`. `<stem>` and `<qualifier>` are each a run of letters, digits, hyphens and underscores. A configuration file in the program is a root. A configuration file no program holds is read all the same, with no type information and no declaration of it judged: its strings are read under the rule below, the specifier of each of its imports and re-exports among them, so an import naming a dependency is a use of the dependency. A file such a file imports by a relative specifier, that no program holds either, is read the same way, and so on until no further file joins. A file outside the target root, or below a `node_modules` directory, is not a file of the project the analysis reads, so no such chain reads it: a relative specifier that reaches one adds no file. Such a relative specifier resolves against the importing file's directory to the first of these paths that names a file:

1. The path the specifier names, where its name ends with one of the extensions of step 3.
2. That path with a final `.js` replaced by `.ts` and then by `.tsx`, a final `.jsx` replaced by `.tsx` and then by `.ts`, a final `.mjs` replaced by `.mts`, or a final `.cjs` replaced by `.cts`.
3. That path with `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs` appended, in that order.
4. Where the path names a directory, the file `index` in that directory with the extensions of the previous step appended, in the same order.

A specifier that reaches no file adds no file and raises no setup failure. A specifier that names a file of another kind, a `package.json` or another JSON file among them, reaches no file, so the strings of a manifest a configuration file imports use none of the dependencies it declares.

A JSON configuration file is a file in the directory of a `package.json` the analysis reads, below the target root and in no `node_modules` directory, whose name is `<stem>.config.json`, `<stem>.<qualifier>.config.json`, `.<stem>rc` or `.<stem>rc.json`. It holds no declaration and is read for its strings alone.

### Strings in configuration

In a configuration file and in a JSON configuration file, every string literal and every template literal with no substitution, at any depth, is read against the `package.json` of the configuration file's directory, which for a file a chain of relative imports reaches is the directory of each configuration file whose chain reaches it, and against the file's own directory:

- A string equal to the name of a dependency that manifest declares, or to that name followed by `/` and a subpath, is a use of the dependency.
- A string that names, read against the file's directory, a source file of the program, directly or with one of the extensions the program's module resolution tries, roots that file, whether or not it starts with `./` or `../`. A string that starts with `/` or holds one of the glob characters `*`, `?`, `[` and `{` names no file.

A JSON object member's name is not read as a string. A string at a selection key of an applied convention row roots no file, as the convention rows below state, and a string in the configuration of a tool no applied row describes is read by this rule alone.

### Script entries

Each value of the `scripts` member of a `package.json` the analysis reads is split at white space and at the shell operators `&&`, `||`, `;` and `|`, and each token, with one pair of enclosing quotes removed, is read against the manifest's directory. A token that names a file of the program, directly or through the emit mappings that read an output file back to its source, roots that file. A token equal to the name of a command that the installed manifest of a dependency the manifest declares names in its `bin`, the package's own name without its scope where `bin` is a string, is a use of that dependency. A token of a script entry that names, read against the manifest's directory, a file whose name ends with `.js`, `.mjs` or `.cjs`, below the target root, in no `node_modules` directory and held by no program, and that holds none of `$`, a backquote, `{`, `~` and the glob characters `*`, `?` and `[`, starts the configuration-file chain at that file, read against that manifest: its strings, and those of each file it imports, re-exports or loads by a relative specifier, are read as a configuration file's are. A token of a workflow step or a git hook that names such a file starts the chain read against the target root's manifest.

### Workflow steps

A workflow file is a file whose name ends with `.yml` or `.yaml` in the directory `.github/workflows` of the target root. It is read as text, line by line, with no YAML parsed. A line whose text after its indentation, and after one sequence marker, a hyphen and a space, starts with `run:` holds a run command. The command is the rest of that line, with its surrounding white space and one pair of enclosing quotes removed. Where that rest is a block scalar indicator, `|` or `>` with an optional `+` or `-` after it, the command is instead each following line indented further than the column where `run:` starts, up to the first non-blank line that is not. Each line of a command is split as a script entry is, at white space and at the shell operators `&&`, `||`, `;` and `|`, with one pair of enclosing quotes removed from each token, and a `#` is read as any other character. A token that names a source file of the program by its whole path relative to the target root, with or without a leading `./`, roots that file, whatever directory the step runs in. No extension is tried and no emit mapping is read. A token that holds `$`, `{` or one of the glob characters `*`, `?` and `[` names no file, because a computed command is not read. A token equal to the name of a command that a dependency of a manifest the analysis reads declares is a use of that dependency, as it is in a script entry, whatever directory the step runs in.

A git hook is read as a workflow step's run command is: every line of each file directly in the directories `.husky` and `.githooks` of the target root, up to a `#` that starts a word outside quotes, because each such file is a shell script and the shell reads no comment, each command a `run:` line of `lefthook.yml`, `lefthook.yaml` or `.lefthook.yml` holds, and each command an `entry:` line of `.pre-commit-config.yaml` holds, the last two read as a workflow file's `run:` lines are, so a token of one roots a file and uses a dependency as a workflow step's token does.

The target root's makefile, the first of `GNUmakefile`, `makefile` and `Makefile` it holds, is read as text for its recipe lines alone: a line that starts with a tab, joined with each line a trailing `\` continues it onto, with its leading `@`, `-` and `+` removed, up to a shell comment as a git hook's line is. A recipe line is read as a workflow step's run command is. Make runs each recipe line in a shell of its own, so a `cd` command naming one directory that holds none of `$`, `{` and the glob characters moves the directory the later commands of that line run in, and a token of such a later command that names a source file of the program read against that directory roots that file.

### Manifest entries

Each entry point a `package.json` the analysis reads names, its `main`, `module`, `types` and `bin` and every target of its `exports`, is read back to a source file of the program: the file the target names where the program holds it, else the file the emit mappings of the workspace rule above read it back to. A target neither reads back to is read against each configuration as if the manifest's directory were its output directory, back to the configuration's root directory, so `./index.js` of a package published from its build directory reads back to `<rootDir>/index.ts`. A target that names a file no program holds is read as a configuration file outside the program is, and each program file a relative specifier of its imports, its re-exports and its `require()` and `import()` calls with a literal names, read through the emit mappings, and so on through each file of that chain no program holds, is the entry point. A target that neither reads back to a source file is read back by name to the files the configuration-file, script-entry and HTML-entry rules of this section root. Its name is its path relative to the manifest's directory below its first directory, or the whole path where it names no directory, without its output extension, being `.d.ts`, `.d.mts`, `.d.cts`, `.js`, `.mjs`, `.cjs` or `.jsx`. A rooted file of the manifest's own package, no `package.json` between them, whose path relative to the manifest's directory, without its source extension, ends with that name at a directory boundary is the entry point, so `dist/cli/main.js` reads back to a rooted `src/cli/main.ts`. Every file that matches is the entry point, for the roots and for a library's published API alike, and a target that reads back to no file roots nothing.

### Release tags

In a library, a published workspace member of an application included, an exported TypeScript declaration whose documentation comment holds the release tag `@public`, `@beta` or `@alpha` is published API, as a declaration a manifest entry reaches is, and so is each public member of a type it declares. Its documentation comment is the last `/** */` comment before it with only white space between the two. A tag is written as `@` and its name, after white space or the comment's opening and before white space or the comment's end. Such a declaration is live under reachability alone, as the published API is, and a finding about it carries the reachability class the confidence rule below gives the published API. That class is `possible` when the run holds no consumer information, `probable` when a declared consumer did not load, and `certain` when every declared consumer loads, so a tagged declaration no loaded consumer uses is reported at `certain`. Elsewhere in an application the tags mark nothing, because an application has no published API outside its published workspace members.

### HTML entry files

A file whose name ends with `.html`, below the target root and in no `node_modules` directory, is an HTML entry file, read as text as a component file is, with no markup parsed. A `<script` start tag whose `type` attribute is `module` begins a module script, and one inside an HTML comment begins one too, because no markup is parsed. A module script with a `src` attribute roots the file `src` names, and so does a classic script, one whose start tag carries a `src` attribute and either no `type` attribute or a `type` of `text/javascript` or `application/javascript`, because the page runs the file either way. One without roots each file that a specifier starting with `/`, `./` or `../` names, of an import or a re-export declaration in its content up to the next `</script>` end tag. An attribute is written `name="value"`, `name='value'` or `name=value`, and its name compares without regard to case. A value or a specifier that starts with `//` or with a scheme and a colon, `https:` among them, names no file. One that starts with a single `/` is read against the directory of the nearest `package.json` at or above the HTML file, and any other against the HTML file's own directory. Either resolves as a relative specifier of a configuration file does. A value or a specifier that names no source file of the program is read back through the emit mappings of the workspace rule above, applied to every configuration of the run: an output file of a configuration's output directory or declaration directory maps to the source file of the same name below its root directory, so a page that loads compiled output roots the source that emits it. A value that starts with a single `/` is read as well against each configuration's output directory whose top holds the HTML file, because a server whose root is that directory serves the page. One that reads back to no source file roots nothing. A file a script element roots is a root as an entry of `ts.entry_files` is.

### Markdown and MDX documents

A file whose name ends with `.md` or `.mdx`, below the target root and in no `node_modules` directory, is read as text: a line outside a fenced code block that starts with an import declaration roots the source file its relative specifier names, on disk or through the emit mappings, as an MDX compiler hoists the import into the module it builds, and with it the exports the import reads: `default` for a default binding, each name its braces list, every export for a namespace import or a clause this reading does not parse, and none for an import written for its effects alone.

### Computed loads

An `import()` or `require()` call whose argument is a template literal or a concatenation whose leading literal part is a relative specifier ending in `/` roots every source file below the directory it names, read against the calling file's directory, with each file's export table, as a bundler's context module loads them; a leading part naming the calling file's own directory, or a directory that holds it, roots nothing, because it would name every sibling. An `import.meta.glob` call whose argument is a relative string literal glob, or an array of them, roots every source file the glob matches against the calling file's directory, with its export table.

### Type-query aliases

An ambient global declaration in a declaration file whose type is `typeof import(<string>)[<string>]`, or `typeof import(<string>).<name>`, is an alias of the declaration that names the module the first string names exports under the second string or the name. A reference to the global is a reference to that declaration and to every link of the alias chain that reaches it, and the type query in the global's own declaration is not a reference. No finding is reported about the global declaration itself.

### Go packages no build links

In an application, a Go package of the target that no build the run sees links is dead with every declaration it holds: no main package, test, program or consumer the run loads imports it, directly or through other packages, and the run read its module whole. Such a package's `init` functions and blank declarations run only when the package is linked, so neither is a root there. A run that declares no consumer classes every declaration of such a package outside an `internal` tree `possible`, because outside programs may import the package, and one under an `internal` tree `certain`; a run that declares consumers has named the outside programs, so its classes are those of any other declaration. A file finding about such a package keeps its class.

### Go generators

A `//go:generate` directive names the inputs of the generator it runs, the program its first word names or the program `go run` or `go tool` names after it, by its base name and without a version. For `stringer` and `enumer` the inputs are the types its `-type` flag lists, in the directive's own package. For `mockgen` they are every interface the file its `-source` flag names declares, read against the directive's directory, or, in package mode, the comma-separated names of its last argument in the package its second-to-last argument names, `.` naming the directive's own package. The directive's words are the ones `go generate` splits it into, a double-quoted string being one word, and `$GOFILE` and `$GOPACKAGE` expand in each word. A flag written without `=` takes the next word as its value unless that word is a flag, or the flag is one of the generator's boolean flags. Every input is a root, and so is every method an input interface declares, because deleting either breaks `go generate`.

A function named `Fuzz`, or `Fuzz` followed by a name that does not open with a lower-case letter, of type `func([]byte) int`, in a file whose build constraint names the `gofuzz` tag outside a negation, is a root, because go-fuzz calls it by name.

A declaration whose doc comment holds a line that opens with `swagger:` is a root, and so is every field of a struct type it declares, an anonymous struct's fields included, because the go-swagger generator reads each one.

### Convention rows

An analyzer may carry a table of convention rows, each the data of one framework's file-system conventions. A row has a name, an enabling package, a version range in the semantic-versioning range syntax, the globs of its entry files, the globs of the files it excludes, the directories its framework generates, the configuration properties that move a directory those globs name, each with the configuration files the property is read from and, for a property that is an option of a call, the module and the exported name of the function called, the configuration properties whose value names a package by a short name, each with the configuration files it is read from and the package name the value stands for, written with `{}` where the value goes, the selection keys, the configuration properties whose value only selects files to test, to mutate, to cover or to ignore, each with the configuration files it is read from, the package keys, the members of a configuration file whose strings name the packages its tool loads, each with the configuration files it is read from, the manifest keys, the members of a `package.json` its tool reads its configuration from, the manifest entry keys, the members of that `package.json` whose strings name the tool's entries, each naming a directory of entries or one entry, the prefixed-name properties, the configuration properties whose value names a package by its tool's prefix convention, each with the configuration files it is read from, the prefix and the marker a value starts with, if any, and the test-file properties, the configuration properties whose value names a file the tool's test runner loads beside the tests, each with the configuration files it is read from and the properties its paths resolve against. The table is part of the analyzer, versioned with it, and no configuration key adds a row.

A row applies when a `package.json` the analysis reads declares the enabling package as a dependency, a development dependency, a peer dependency or an optional dependency, and the version the installed package's own `package.json` names, found from that manifest's directory as the compiler resolves a package, is in the row's range. An enabling package declared as a dependency or a development dependency whose installed manifest the analysis cannot find is the setup failure `missing-module`, except in a nested package's manifest, where it applies no row and raises no setup failure, because no run requires a nested package to be installed. An enabling package declared only as a peer dependency or an optional dependency whose installed manifest the analysis cannot find applies no row and raises no setup failure. An applied row's globs are matched against the directory of the manifest that declared the package, each against a source file's own path and against each output path the emit mappings of the configuration holding the file write it to, so a glob naming build output names the source that output is compiled from: every file an entry glob matches and no exclude glob matches is a root, as an entry of `ts.entry_files` is, and every file below a directory the row names as generated, read against the same directory, is a generated file, whose declarations the `generated-file` class of [`exemptions.json`](../exemptions.json) retains.

A property that moves a directory is read from the row's configuration file without running it, in the objects the row reads there. Where the property is not an option of a call, the object is the file's default export, in each of its forms: the expression `export default` writes, the value assigned to `module.exports`, the binding an `export { name as default }` specifier names, and the document of a JSON configuration file. A default export that names a top-level `const`, `let` or `var` binding is read through to that binding's initializer, and one that is a call is read through to the call's first argument, until an expression that is neither. Where the property is an option of a call, the objects are the first arguments of every call in the file to the row's function, imported from the row's module by its exported name under any local name, or called through a namespace import of that module; an argument that names a top-level binding is read through to its initializer, and no further call is followed. In a file that declares no binding named `require`, a top-level `const`, `let` or `var` declaration whose initializer is a call of `require` with the row's module as its one argument, written as a string literal, binds as an import of that module does. An object binding pattern binds each exported name it lists under its local name, as a named import does, and a binding that is a name binds a namespace import. Parentheses, `as`, `satisfies` and the non-null assertion are read through wherever an expression is. A call with no argument, and a file with no object to read, set nothing.

The property is a path of keys through nested object literals, each key matching a property whose name is an identifier, a string literal or a template literal with no substitution, or a computed name whose expression is a string literal or a template literal with no substitution. Where the value at the end of the path is a string literal or a template literal with no substitution, the globs read each directory so set; where no object the row reads sets the property, the globs read the default directory. The row is the setup failure `convention-not-literal` where the value at the end of the path is anything else, a template literal with a substitution, a concatenation, a call and a name among them; where a value along the path is not written as an object literal, a name bound to an object literal among them, because a key's value is not read through a declaration; where the object the row reads is not written as an object literal, a default export that is a function or a class among them; and where the object the row reads or an object along the path holds a spread, or a computed name whose expression is not a string literal, a numeric literal or a template literal with no substitution, because either may set any key. An object the row does not read, the options of another function in the same file among them, sets nothing and raises no failure.

A property that names a package by a short name is read from an applied row's configuration files as a property that moves a directory is, and a string value at the end of its path, or a string element of an array value there, stands for the package name the row writes with that string in place of `{}`. A declared dependency of that name is used. Where the value is not a literal, every declared dependency whose name the row's package name can produce with some value in place of `{}` is used, and the row raises no setup failure for the property. A string value equal to a declared dependency's own name is a use under the strings rule above whatever the row says.

A prefixed-name property is read as a property that names a package by a short name is, and a string value at the end of its path, or a string element of an array value there, names a package by the prefix convention: a name `x` stands for `<prefix>-x`, a scope `@s` alone for `@s/<prefix>`, a scoped name `@s/x` for `@s/<prefix>-x`, and a name that already starts with `<prefix>-`, or a scoped name whose second part does, for itself. Where the property has a marker, only a value that starts with the marker names a package, its name the text between the marker and the value's last `/`, so `plugin:react/recommended` names `react`. Where it has none, a value holding a `:` or starting with `.` or `/` names none, and the name ends at the value's first `/` past a scope, so `airbnb/hooks` names `airbnb`. A declared dependency so named is used. A value that is not a literal uses nothing under this rule and raises no setup failure.

A selection key is read from an applied row's configuration files as a property that moves a directory is. A string value at the end of its path, or a string element of an array value there, roots no file under the strings rule above, because the tool reads a file it selects only when another key runs or loads that file. A key that runs or loads a file is no selection key, so a string it holds roots the file it names. A selection key whose value is not a literal raises no setup failure, and every string the file holds elsewhere is read under the strings rule.

A manifest entry key is read from the `package.json` that declared the row's enabling package, a key path whose `*` stands for every member of the object it reaches. Every string at any depth of the value there, a JSON object member's name excepted, read against that manifest's directory with leading `./` segments dropped, writes an entry glob: for a key naming a directory, every module below it, and a string holding a glob character names none; for a key naming an entry, the string itself and the string followed by a JavaScript or TypeScript extension. A string that leaves the manifest's directory writes none. The globs are matched as the row's own entry globs are, so a key naming build output roots the source the emit mappings read it back to.

A manifest key is read from the `package.json` that declared the row's enabling package. Every string at any depth of that member's value, a JSON object member's name excepted, that equals the name of a dependency the manifest declares, or that name followed by `/` and a subpath, is a use of the dependency. A string under a member that no applied row names as a manifest key is no use of a dependency under this rule.

A package key is read from each of an applied row's configuration files, in the objects the row reads there as it reads a property that moves a directory, the document of a file whose name ends with `.json` among them. Every string at any depth of the value of a member of that name, a JSON object member's name excepted, at any depth of those objects, that equals the name of a dependency the manifest that declared the row's enabling package declares, that name followed by `/` and a subpath, or that name followed by `:` and a name, is a use of the dependency, so a string `"@example/tool:build"` under a package key `builder` uses `@example/tool`. Such a string uses no other dependency itself, and a string under a member that no applied row names as a package key is no use of a dependency under this rule. A declared peer of a dependency it uses is needed as the precondition of `DS1601` in [`kinds.json`](../kinds.json) states.

A test-file property is read from an applied row's configuration files as a property that moves a directory is. Each string value at the end of its path, or string element of an array value there, read against the directory the row's resolving properties give, or else the configuration file's own directory, names a test file, as a file `ts.test_files` names is one, because the runner loads the file only to run tests. A file a test-file property names is not rooted by the strings rule.

The configuration's own keys win. A row `ts.disabled_conventions` names does not apply, adds no root and raises no setup failure, and the entries of `ts.entry_files` are roots whether a row applies or not. A row only adds roots, uses, retentions and test files. The report lists each row it applied in `conventions_applied`.

## Confidence

A finding's reachability class states what the analysis can see of its subject's users. A subject of a library's published API, a published workspace member's included, is `certain` when every declared consumer loads, `probable` when a declared consumer did not load, and `possible` when the run holds no consumer information. So is each public or protected member of a type the published API reaches, because an outside program holding a value of that type can name the member: the published API reaches the type of each published declaration, of each of its parameters, results and properties and of each constraint of its type parameters, and in turn the type of each member, base type and type argument of a type it reaches, a getter and a setter of one name being one declaration whose types are both reached, the getter's result and the setter's parameter. A published value whose type is a module's namespace reaches each export of that module, and not the module's file. A library's internals, which outside programs cannot name, and every other subject of an application are `certain`, except a declaration of a Go package no build links, as Roots states. A package-level Go declaration whose identifier a string literal spells exactly, a literal whose value equals the identifier, written outside the declaration itself in a production Go file of the target that the run builds, has the reachability class `possible` under `DS1001`, `DS1002`, `DS1004`, `DS1006`, `DS1101`, `DS1102` and `DS1103`. A string literal here is one of an expression, a constant's value included; the path of an import declaration and the tag of a struct field are not counted. Outside the declaration itself means outside the source range of its own declaration node, so a literal in the body of a method declared on a type counts for the type, because the method is a declaration of its own. The own declaration node of a name a grouped `const`, `var` or `type` declaration declares is the specification that declares it, so a literal in one specification counts for a sibling the group declares. The reason is that a tool reading the source, a code generator among them, may find the declaration by that name, and only a text search can tell whether one does. The finding's `details.name_literal` is the position of the first such literal in the order positions sort. A struct field, a method and an interface method are not capped this way, and a literal in a test file caps nothing, as an exemption's evidence in a test file holds nothing in a production sweep. A package-level constant whose type is a defined type of the target that such a literal spells has the same class under the same codes, its `details.name_literal` the literal that spells the type, because a tool that finds a type by its name reads that type's constants. A TypeScript member of a class, an interface or a type literal whose name equals a string literal, or a template literal with no substitution, written as the left operand of an `in` expression in a production file of the target, has the reachability class `possible` under every code. A value narrowed by such an expression is read back by that name, often through `unknown`, where no type links the read to the member, so only a text match can tell which member it reads. Such a finding carries no `details.name_literal`. A finding about a field that the `encoding-reflection` class records only as filled by a callee outside the analyzed program whose name says it fills its argument has the reachability class `possible`, as [`exemptions.json`](../exemptions.json) states. A finding's confidence is its reachability class capped by its kind's `max_class`. A TypeScript finding about a declaration found dead under reachability alone, one that only declarations themselves dead reference, and a `DS1502` finding about a file only dead code imports, is capped as well at `probable` unless `ts.roots_complete` is `true`: a root the analysis does not see, a framework's convention or a computed load, would make the subject live, and only the maintainer can declare that none exists. A finding about a declaration nothing references and an intra-function finding are not capped by it. A finding about a member of a dead component, a root member included, is capped as well by the lowest confidence among the findings about the component's root members, a root's name-literal cap included, so every finding of one component carries one confidence and the minimum withholds or reports the component whole. A test of dead code whose component holds a published declaration therefore carries no higher confidence than that declaration, whatever reachability class the test itself has. `analysis.min_confidence` defaults to `probable`, so a run over a library with no declared consumer withholds the findings about its published API, a run withholds every other finding this section places at `possible`, and every other finding is reported; the dial is the one mechanism that withholds a published API, and no kind's default depends on the target kind. The report's `totals.withheld` counts the findings the minimum withheld, each at the confidence this run assigns it, so its `certain` count is always 0. The text and SARIF outputs name the counts in one line with the setting that shows them, as [`text-line.md`](text-line.md) states.

## Fixability

A finding carries the fixability [`kinds.json`](../kinds.json) gives its kind, unless a rule below gives it another one, which is always one the kind's `finding_fixabilities` lists. A finding about a declaration in a generated file carries `none` under every kind, as the `generated-file` class of [`exemptions.json`](../exemptions.json) states.

### Positional members

A declaration's dependents are the declarations of its group whose value its deletion changes, or leaves undefined:

- In Go, the dependents of a specification S of a parenthesized constant declaration are each later specification of that declaration that repeats S's expression list, being, where S writes one, each specification after S that writes none, up to the next one that does, and each later specification whose expression list, the one it writes or the one it repeats, uses `iota`. Deleting S makes each specification that repeats its list repeat an earlier list, or none where S is the first, and lowers `iota` by one in every later specification, and deleting one of several names S declares, with its expression, changes the length of the list those that repeat it repeat. Where S writes no expression list and declares several names, S is a dependent of itself as well, because deleting one of its names leaves fewer names than the list it repeats has expressions. A constant S declares has the dependents of S, so the rule decides a specification as a whole, whichever of its names are live.
- In TypeScript, the dependents of a member of an `enum` declaration are each later member of that declaration with no initializer, up to the first one with an initializer. Deleting the member moves the value of each of them.

A dependent is live when it declares a constant or a member the analysis holds live under reachability, so a specification that declares only blank names is no live dependent. A dead declaration with a live dependent is a positional member, and a finding about it carries `manual`, whatever its code: its deletion changes a live value, while replacing a Go constant's name with `_` keeps every value, and so does giving a TypeScript member's first dependent an initializer that holds its present value.

No mechanical edit deletes a positional member, so none deletes a declaration its value depends on either. The positional members, each dead declaration that a held declaration references, and each dead declaration of which a held declaration is a dependent, are held, and so on until no further declaration joins: a finding about one of them carries `manual`, and none of them carries `removes_last_use_of`. Their components are the weakly connected parts of the held declarations over the references among them, each with the root members the component rule gives it and `deletable_lines` 0. A reference between a held declaration and a dead declaration that is not held joins nothing, so a dead function that names a held declaration is a component of its own and deletes without it.

A dead declaration that is not held, and each of its dead dependents, none of which is held then, belong to one component, because deleting it alone changes their values and can stop code that uses them from building. The joint is no reference, so it makes no member a non-root member and makes no declaration live. A group whose every declaration is dead is therefore one component and deletes whole, and its findings carry their kinds' own fixability.

## Type errors

A type error the compiler reports in source the program holds does not end the run. The innermost function, method, accessor, constructor, arrow function or function expression whose source holds the error's position is not evaluated, or the class member or the file-level statement holding it where no function does: nothing is reported about it or about any part of it, every reference in it the compiler resolves still counts, and every declaration an expression of it that does not resolve could reach is retained, so the skip can only withhold a finding. A diagnostic the compiler marks as reporting unnecessary code is not a type error for this rule, in any file. Each type error that skipped something is listed in the report's `type_error_skips` with its file, its line and the compiler's message, printed on standard error, and rendered as a warning annotation by the `github` format; the exit code follows the findings.

A type error in a dependency's declarations, outside the program, is not the program's and skips nothing.

A dependency package whose every Go file the analysis's cgo-disabled reading excludes, and that the configuration builds with cgo enabled, is a package of the program the analysis holds no declaration of: a reference to one is a type error of the referencing source, under the rule above, and no setup failure.

## Unanswered questions

A question the analysis asks its type checker that the checker fails to answer is never read as an answer. Every declaration the answer could have made live is held: no finding is reported about it, every liveness relation treats it as live, and a declaration that reads a held binding by name is held too. An unanswered question holds a declared dependency only where its answer is the resolution of a module specifier, and then each dependency a manifest at or above the file that writes the specifier declares. Each configuration in which at least one question went unanswered is listed in the report's `unanswered_questions` with the number of questions and of declarations held.

## Setup failures

A setup failure is a file or a component the analysis needs and the project does not provide. In a configuration the configuration document declares, it ends the run with exit code 3 before any finding list exists, because every missing piece hides real uses and a partial run would report live code as dead. A configuration the analysis derived is dropped instead, as a derived configuration it cannot build is: it is listed in the report's `configurations_not_built` with the failure's line as its `error`, and the run analyzes the configurations left. When the analysis drops every configuration it derived, no matrix is left to analyze, and a setup failure among them ends the run as a declared configuration's does. A configuration whose `extends` chain returns to a configuration it already passed, or that references, directly or through other references, a configuration whose chain does, cannot be built, and the analysis refuses it before any program is built: a derived one is dropped and listed in `configurations_not_built` with an `error` carrying the compiler's code `TS18000` and the chain, and one the configuration document or the invocation names ends the run with exit code 3. A global type the compiler's checker needs that no library of the program declares, an error the compiler places in no file, leaves the configuration built, as a type library it cannot find does: the checker types every use of it against nothing and places no error in the files, so each file of the configuration is a unit a type error skips, from its first line to its last, listed in `type_error_skips` at its first line with the compiler's message, and the run notes the missing type on standard error. A type library or a lib the configuration names that the compiler cannot find leaves the configuration built, because a use of a name only that library declares is an error in its file, a type error under the rule above, and the run notes the missing library on standard error. An error about a compiler option that the compiler places in no file, a removed option or an output layout among them, leaves the configuration built and is not reported, because the compiler checks the whole program all the same. For each failure that ends the run, the run prints one line on standard error that starts with `setup failure:`, a space, the class, a colon and a space, and names what is missing and the fix:

- `setup failure: missing-module`: an import names a module the project expects to exist and nothing provides it. A module the project expects is a module of the target's own module, a path its configuration maps to no existing file, unless the specifier names a package installed in a `node_modules` directory at or above the importing file, where the compiler looks after `paths`, a declared dependency that no `node_modules` directory at or above the importing file's directory holds, where the nearest manifest declaring it is the target's or a workspace member's, because no run requires a nested package to be installed, so the import of a nested package's dependency that nothing installs is a type error of the importing statement, a workspace member, and a module under a directory the project's ignore rules leave to a generator or a build. An import the compiler cannot resolve of a file that exists, a path mapping's target included, and of a package installed in a `node_modules` directory at or above the importing file, the target root's ancestors included, is a type error of the importing statement: the file is provided, and the import names something the file or the package does not give it. The fix names the import, the file that writes it, and the generator, the build or the install to run.
- `setup failure: incomplete-module-sum`: the Go module sum file lacks a checksum the build needs. The fix is `go mod tidy` in the module that requires it.
- `setup failure: missing-consumer`: a declared consumer is absent from the path the scope names, or its own dependencies are not installed. The fix names the consumer, the path and the install.
- `setup failure: workspace-member-without-source`: a workspace member import reads back to no source file. The fix names the member, the subpath, the importing file and the targets the manifest names, and asks for a build of the member or an output and root directory that map the target to its source.
- `setup failure: convention-not-literal`: an applied convention row's directory property is not a literal. The fix names the configuration file and the property, and the alternative of disabling the row in `ts.disabled_conventions` and naming the files in `ts.entry_files`.

A configuration the invocation or the configuration document names that cannot be read ends the run with exit code 3 as well, and so does a run that needs more memory than the machine makes available, which prints the line `memory_exhaustion` in [`exit-codes.json`](../exit-codes.json) states.

## Notes

A note is a hint about the run's setup that the analysis cannot decide. It is no finding: the findings beside it are reported as they would be without it, and it fails no run.

- `module-not-loaded`: a Go module below the target root that the run dropped because it does not load, as "The Go modules of a target" states. The note names the module's directory relative to the target root and carries no `key`, because no configuration key settles it; its message ends with the first line of the failure.
- `published-package`: a Go package of an application, not a `main` package and not under an `internal` directory, that no file of another package of the target, no program of the target under the `ignore` tag and no module or package the run loads as a consumer of its own tree imports. Outside programs may import such a package, and only the user knows whether they do; the note names the package's directory, relative to the target root and written `.` for a package at the root itself, and `roots.patterns`, the key that roots its published declarations.
- `unmapped-entry`: a manifest entry, a `main`, `module`, `types` or `bin` member or an `exports` target, that reads back to no source file of any configuration of the run, and by name, as Manifest entries reads a target back, to no file that `ts.entry_files` or another entry of the manifest roots. It roots nothing, so the findings its file would have rooted are reported; the note names the directory of the manifest, relative to the target root and written `.` for the root, and `ts.entry_files`, the key that names the file it is built from.
