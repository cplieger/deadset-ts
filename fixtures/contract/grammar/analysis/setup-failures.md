# Setup failures

Rules `setup-failures.1` to `setup-failures.8` of [the analysis](../analysis.md). A rule is cited by its id, which is never reused for another rule.

**setup-failures.1** A setup failure is a file or a component the analysis needs and the project does not provide. In a configuration the configuration document declares, it ends the run with exit code 3 before any finding list exists, because every missing piece hides real uses and a partial run would report live code as dead. A configuration the analysis derived is dropped instead, as a derived configuration it cannot build is: it is listed in the report's `configurations_not_built` with the failure's line as its `error`, and the run analyzes the configurations left. When the analysis drops every configuration it derived, no matrix is left to analyze, and a setup failure among them ends the run as a declared configuration's does. A configuration whose `extends` chain returns to a configuration it already passed, which the compiler reports with the code `TS18000` when it parses the configuration, cannot be built, and the analysis refuses it before any program is built: a derived one is dropped and listed in `configurations_not_built` with an `error` carrying `TS18000`, the compiler's message and the configuration's path, and one the configuration document or the invocation names ends the run with exit code 3. A configuration that only references such a configuration is built as the compiler builds it. A global type the compiler's checker needs that no library of the program declares, an error the compiler places in no file, leaves the configuration built, as a type library it cannot find does: the checker types every use of it against nothing and places no error in the files, so each file of the configuration is a unit a type error skips, from its first line to its last, listed in `type_error_skips` at its first line with the compiler's message, and the run notes the missing type on standard error. A type library or a lib the configuration names that the compiler cannot find leaves the configuration built, because a use of a name only that library declares is an error in its file, a type error under the rule above, and the run notes the missing library on standard error. An error about a compiler option that the compiler places in no file, a removed option or an output layout among them, leaves the configuration built and is not reported, because the compiler checks the whole program all the same. For each failure that ends the run, the run prints one line on standard error that starts with `setup failure:`, a space, the class, a colon and a space, and names what is missing and the fix:

- **setup-failures.2** `setup failure: missing-module`: an import names a module the project expects to exist and nothing provides it. A module the project expects is a module of the target's own module, a path its configuration maps to no existing file, unless the specifier names a package installed in a `node_modules` directory at or above the importing file, where the compiler looks after `paths`, a declared dependency that no `node_modules` directory at or above the importing file's directory holds, where the nearest manifest declaring it is the target's or a workspace member's, because no run requires a nested package to be installed, so the import of a nested package's dependency that nothing installs is a type error of the importing statement, a workspace member, and a module under a directory the project's ignore rules leave to a generator or a build. An import the compiler cannot resolve of a file that exists, a path mapping's target included, and of a package installed in a `node_modules` directory at or above the importing file, the target root's ancestors included, is a type error of the importing statement: the file is provided, and the import names something the file or the package does not give it. The fix names the import, the file that writes it, and the generator, the build or the install to run.
- **setup-failures.3** `setup failure: incomplete-module-sum`: the Go module sum file lacks a checksum the build needs. The fix is `go mod tidy` in the module that requires it.
- **setup-failures.4** `setup failure: missing-consumer`: a declared consumer is absent from the path the scope names, or its own dependencies are not installed. The fix names the consumer, the path and the install.
- **setup-failures.5** `setup failure: workspace-member-without-source`: a workspace member import reads back to no source file. The fix names the member, the subpath, the importing file and the targets the manifest names, and asks for a build of the member or an output and root directory that map the target to its source.
- **setup-failures.6** `setup failure: convention-not-literal`: an applied convention row's directory property is not a literal. The fix names the configuration file and the property, and the alternative of disabling the row in `ts.disabled_conventions` and naming the files in `ts.entry_files`.
- **setup-failures.7** `setup failure: no-program`: the run holds no program of a language it analyzes, as The program states. The fix names the target root and the files the language reads a program from, and asks for a run from the directory that holds them or for the languages to analyze.

**setup-failures.8** A file the invocation names that cannot be read, a configuration document, a scope document or a template, ends the run with the usage code 2 before any analysis, because the fix is to the command line. A file a configuration document names that cannot be read ends the run with exit code 3 as well, and so does a run that needs more memory than the machine makes available, which prints the line `memory_exhaustion` in [`exit-codes.json`](../../exit-codes.json) states.
