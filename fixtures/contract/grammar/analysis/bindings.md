# Schema bindings

Rules `bindings.1` to `bindings.20` of [the analysis](../analysis.md). A rule is cited by its id, which is never reused for another rule. These rules are followed by the analyzed languages of [`languages.json`](../../languages.json), the rows of `kind` `analyzed`: they state what a language analyzer publishes about code a schema generator wrote, which [the schema reader's rules](schemas.md) and [the merge](../merge.md) then read. Each generator's own identity rules are on the references page of its language.

## The facts document

**bindings.1** An analyzer asked with `--facts=<path>` writes one facts document, an instance of [`facts.schema.json`](../../facts.schema.json) whose `language` is its own, to the path, after its report and through the same atomic write. Asked without it, it writes none. The report it writes is the same byte for byte with and without the option, and the option changes neither its exit code nor any note it writes, so implementer records, the registration cut, `cap` and every generated file a row does not support exist in the facts document alone.

**bindings.2** The document's `generated` lists every file the analysis recognises as generated, one entry per file, by the one decision the `generated-file` class of [`exemptions.json`](../../exemptions.json) reads, so a file is generated in the facts exactly when that exemption holds its declarations. The entry's `evidence` names what decided it, its `line` is the 1-based line of the comment line that marks the file, the first line a do-not-edit notice of more than one line is on included, or 1 for a convention row, and its `detail` is that line's text, or the convention row's name.

**bindings.3** A generated file matches the first row of [`generators.json`](../../generators.json), in that document's order, whose `language` is the analyzer's, whose `header` matches a line of the file's leading comments, whose `runtime_import`, where the row names one, the file imports, whose version interval, where the row names one, holds the version the output states, and whose option set the output meets. Its entry then carries `generator`, the row's `id` with the version the output states, if any, and `schema_files`, the import paths of the schema files the output names as its sources, as the references page of its language states where each generator writes them. An entry no row matches carries neither.

**bindings.4** An output a row with a version interval matches, whose identity the analyzer cannot decode by that row, ends the run with `setup-failures.12`, because the row is wrong for an output it states it covers. An output of the same major outside every interval of its rows, or an output that states no version, that the row cannot decode binds as a fallback of scope `all` (`bindings.7`), because the generator changed its shape after the row was written.

## Records

**bindings.5** A binding record names, by its `schema` and `schema_file`, the schema declaration it binds as the generator wrote it: `schema` is the declaration's `proto://` reference, which [the reference grammar](../symbol-ref.md) spells from the package and the dotted name the output carries, and `schema_file` is the import path the output names, never rewritten against any root. The merge matches a record to a schema record by both, as [the merge](../merge.md) states.

**bindings.6** A `consumer` record is published for each generated declaration the role column of its file's row lists as a consumer, its `symbol` the declaration's reference in the analyzer's language, its `generated_file` the entry it was read from. A consumer of a service is each declaration the row names as standing for the whole service; a consumer of an RPC is the client's method for that RPC. A declaration the output declares more than once, as overload signatures, is one record.

**bindings.7** A `fallback` record is published for each generated file whose row's cell is `fallback`, with `scope` `all`, or `rpc-types-fallback`, with `scope` `types`, its `symbol` the file's own reference (the `:file` form in Go, the module in TypeScript) and its `state` `live`, once per schema file its entry names. A file whose cell is `serializer-only`, `exposure-only` or `unsupported` publishes no record; its row lists what it does instead.

**bindings.8** An `implementer` record is published for each method of a hand-written type outside test code that implements a method of a generated server or handler interface, where the production sweep's `interface-satisfaction` exemption names that interface for the type, whatever site writes the conversion. Its `symbol` is the method's reference, and its `schema` the RPC the interface method stands for. A method the generated `Unimplemented` type supplies is no implementer.

**bindings.9** A registration form binds nothing: a call of the row's registration function, a conversion of a hand-written type to the generated server or handler interface, a satisfaction assertion, an embedding of the row's `Unimplemented` or `Unsafe` type, and a reference to a constant that names the service for registration, reflection or health checks. A constant that names one RPC's full method name or procedure is an identity source of the output and binds nothing either, so an allow-list naming it calls nothing.

## States

**bindings.10** A document whose `evaluated` is `false` publishes identities only: no consumer or implementer record carries `state`, `via`, `cap`, `finding` or `carried`. The merge reads such a record `live`, so identity facts keep every schema declaration they bind and promote nothing. An analyzer writes `evaluated` `true` only once every rule of this section that can change a published state is applied, and then every consumer and implementer record carries a `state`.

**bindings.11** A binding state is computed by a carrier sweep, a second sweep of the production graph in which no declaration of a generated file is a root, its initialisers, package-level variables and blank assertions included, and an exemption seeds the sweep only when its evidence site is in a hand-written file. The production sweep, its findings and its report are unchanged by it.

**bindings.12** In the carrier sweep, a reference a generated declaration makes is followed only from a generated declaration the sweep already reached from hand-written code, so a hand call of a getter reaches the getter and the getter's read reaches its field, and a message's own reflection methods reach descriptor data that binds nothing.

**bindings.13** In the carrier sweep, generated transport, forwarding, dispatch and registration are not followed, and nothing else is cut: the references each row lists from generated code into its RPC runtime, a hand-written site passing a message to an RPC runtime, a gateway's forwarding calls, a generated selection of a server or handler interface method, the `interface-satisfaction` exemption whose detail names a generated server or handler interface, and a generated registration function's own references. A hand-written selection of a generated server or handler interface method, a call or a method value through a value of the interface type, reaches the method of every implementer record of that interface method. A hand-written method declared on a generated type is followed as any hand reference is.

**bindings.14** A write of a field reaches nothing, so hand code that only sets a field makes no binding of it live, while a reference to a message type, a literal of it or a construction of it included, keeps the type's binding live. A oneof member is read where hand code tells the member apart from its siblings, as the references page of each language states the forms, and a read of the oneof that tells no member apart reads every member.

**bindings.15** A hand-written call of a serializer that encodes a message reads every field reachable from the call's static message type through field types, because the bytes, text and sizes it produces are observable; a decoding call writes; a clone passes its argument through. The serializers are a closed list on the references page of each language. A serializer reached only through generated transport reads nothing.

**bindings.16** A `consumer` record is `live` when the carrier sweep reaches its declaration or a rule whose evidence site is in a hand-written file retains it, `live` with `via` when only implementer methods reach it, `via` naming the `symbol`s of those implementer records, and `unreferenced` otherwise. A consumer, whatever its state, carries `cap` `persistence` when hand code decodes its message type from ProtoJSON without discarding unknown fields, and `cap` `descriptor-exposure` when hand code serves its file's descriptors through server reflection or converts them to descriptor messages. Where `possible` is below `analysis.min_confidence` the record carries no `cap`, because the merge must not lower a finding below the minimum it was published under.

**bindings.17** An `implementer` record is `live` when the carrier sweep reaches its method, and `dead` otherwise, carrying the pending finding the method's own references select, never a schema code. A dead implementer that another implementer's survival alone would keep carries `via` naming that implementer, and the findings of the hand-written declarations only its own search reaches as `carried`, each in its finding's component. A record whose finding lies below `analysis.min_confidence` is published `live`.

**bindings.18** A finding a facts document carries is never one its paired report reports: its component id is minted under the analyzer's name from the report's component sequence onward, so no id the report names is reused, and its `symbol.ref` names a symbol the report holds no finding for, as the `interface-satisfaction` exemption already retains every implementer in the report.

**bindings.19** Records are written in the order and with the uniqueness [`facts.schema.json`](../../facts.schema.json) states, and a reference in a `via` names a record of the same document and never the record's own `symbol`.

**bindings.20** A file whose row's cell is `unsupported` is a `generated` entry like any other and publishes no record. The merge, not the analyzer, writes the `binding-unsupported` note it makes, so the analyzer's report stays the same.
