# Roots

Rules `roots.1` to `roots.29` of [the analysis](../analysis.md). A rule is cited by its id, which is never reused for another rule.

**roots.1** A root is live without a reference. Beside the roots `roots.patterns` and `ts.entry_files` configure, the entry points a manifest names and a library's published API, the TypeScript analysis marks the roots below, and the Go analysis those of the subsections whose title names Go. A root that names a file roots the file's top level and everything its export table names, a re-export walked to the declaration it carries, and is live under both liveness relations, because a program the project runs loads it.

## Configuration files by name

**roots.2** A file in the directory of a `package.json` the analysis reads, below the target root and in no `node_modules` directory, is a configuration file when its name is `<stem>.config.<ext>` or `<stem>.<qualifier>.config.<ext>`, with `<ext>` one of `js`, `mjs`, `cjs`, `ts`, `mts` and `cts`, or `.<stem>rc.<ext>`, with `<ext>` one of `js`, `mjs` and `cjs`. `<stem>` and `<qualifier>` are each a run of letters, digits, hyphens and underscores. A configuration file in the program is a root. A configuration file no program holds is read all the same, with no type information and no declaration of it judged: its strings are read under the rule below, the specifier of each of its imports and re-exports among them, so an import naming a dependency is a use of the dependency. A file such a file imports, re-exports, or loads by an `import()` call or a `require()` call as `conventions.3` reads one without a checker, by a relative specifier written as a string literal or a template literal with no substitution, that no program holds either, is read the same way, and so on until no further file joins. A file outside the target root, or below a `node_modules` directory, is not a file of the project the analysis reads, so no such chain reads it: a relative specifier that reaches one adds no file. Such a relative specifier resolves against the importing file's directory to the first of these paths that names a file:

1. **roots.3** The path the specifier names, where its name ends with one of the extensions of step 3.
2. **roots.4** That path with a final `.js` replaced by `.ts` and then by `.tsx`, a final `.jsx` replaced by `.tsx` and then by `.ts`, a final `.mjs` replaced by `.mts`, or a final `.cjs` replaced by `.cts`.
3. **roots.5** That path with `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs` appended, in that order.
4. **roots.6** Where the path names a directory, the file `index` in that directory with the extensions of the previous step appended, in the same order.

**roots.7** A specifier that reaches no file adds no file and raises no setup failure. A specifier that names a file of another kind, a `package.json` or another JSON file among them, reaches no file, so the strings of a manifest a configuration file imports use none of the dependencies it declares.

**roots.8** A JSON configuration file is a file in the directory of a `package.json` the analysis reads, below the target root and in no `node_modules` directory, whose name is `<stem>.config.json`, `<stem>.<qualifier>.config.json`, `.<stem>rc` or `.<stem>rc.json`. It holds no declaration and is read for its strings alone.

## Strings in configuration

**roots.9** In a configuration file and in a JSON configuration file, every string literal and every template literal with no substitution, at any depth, is read against the `package.json` of the configuration file's directory, which for a file a chain of relative imports reaches is the directory of each configuration file whose chain reaches it, and against the file's own directory:

- **roots.10** A string equal to the name of a dependency that manifest declares, or to that name followed by `/` and a subpath, is a use of the dependency.
- **roots.11** A string that names, read against the file's directory, a source file of the program, directly or with one of the extensions the program's module resolution tries, roots that file, whether or not it starts with `./` or `../`. A string that starts with `/` or holds one of the glob characters `*`, `?`, `[` and `{` names no file.

**roots.12** A JSON object member's name is not read as a string. A string at a selection key of an applied convention row roots no file, as the convention rows below state, and a string in the configuration of a tool no applied row describes is read by this rule alone.

## Script entries

**roots.13** Every command string the analysis reads is read in three layers, without running it, in the directory it runs in: each value of the `scripts` member of a `package.json` the analysis reads and the `exec` command of nodemon's configuration, in the manifest's `nodemonConfig` member or in the `nodemon.json` beside it, in the manifest's directory, and each command string of a workflow step, a git hook and a makefile recipe line, in the directory `roots.15` to `roots.17` give it, or in one the analysis does not know where `roots.15` says so. The first layer parses the string as a POSIX shell command line, with a shell parser rather than by splitting it at characters, into its simple commands, each a program word and its argument words, joined by `&&`, `||`, `;`, `|`, `&` and newlines, with quotes, backslash escapes, line continuations and comments read as the shell reads them. A word that holds a parameter expansion, a command substitution, an arithmetic expansion, a process substitution, one of the glob characters `*`, `?` and `[` outside quotes, a brace expansion or a leading `~` outside quotes is dynamic: its value is not known. An assignment written before a program word, a redirection, a here-document, a compound command, a function definition and a command with no program word are not read as words, and a string any part of which does not parse is read as no command at all. The second layer reads each simple command whose program word is the name of a tool it has a reader for, or a path whose last segment is such a name, `node_modules/.bin/tsx`, `/usr/bin/node` and `"$(npm root)/.bin/tsx"`, whose last segment is written after a `/` though the run computes the rest, among them, with or without the `.exe` or `.cmd` a Windows program's name ends with, `node.exe` and `npx.cmd` among them, by that tool's reader, which reads only the options the tool documents for choosing the file it runs, a module it loads before that file, or the command it runs: `node`'s `-r`, `--require`, `--import`, `--loader` and `--experimental-loader`, each with its value as the next word or, for a long option, after `=`, and the options it documents that leave the file it runs where it is, `--no-warnings`, `--enable-source-maps`, `--watch`, `--input-type`, `--env-file` and `-C` among them, `--inspect`, `--max-old-space-size` and `--stack-size` taking a value only after `=`, and its test options, while `--test` runs its test runner in the file's place on the files its operands, or its default patterns, name, which `tests.1` reads where a manifest's script writes the command and the command runs a file no word writes elsewhere, as does a pattern that is dynamic or a glob ([node](https://nodejs.org/api/cli.html)), with its first operand as the file it runs, which it runs under Node; `tsx`'s `-r`, `--require`, `--import`, `--tsconfig` and `--no-cache` and those of `node` but `--test` ([tsx](https://tsx.is/node-enhancement)), after an optional `watch`, and `ts-node`'s `-r`, `--require` and `--esm`, each with its first operand as the file it runs; `bun`'s `-r`, `--preload`, `--watch`, `--hot`, `--smol`, `--bun`, `--silent` and `--no-install`, before and after an optional `run` ([bun run](https://bun.com/docs/cli/run)), and `deno`'s `-A`, `--allow-all`, `-q`, `--quiet`, `--watch`, `--no-check` and its `--allow-` permissions written without a value, after an optional `run` or `serve` ([deno run](https://docs.deno.com/runtime/reference/cli/run/)), each with its first operand as the file it runs and none where that operand is another of the tool's subcommands, `bun install`, `bun test` and `deno task` among them, which `deno` finds only past its `-q` and `--quiet`, so `deno -A lint` runs `lint` ([deno's parser](https://github.com/denoland/deno/blob/main/libs/cli_parser/src/parse.rs)), and `bun x`, which runs as `bunx`; `node`'s `-e`, `--eval`, `-p`, `--print` and `--run`, and `ts-node`'s and `bun`'s `-e`, `--eval`, `-p` and `--print`, each with its value as the next word or after `=`, which run that value in the file's place, so the command runs no file, and `node` given no file, or `-`, runs its standard input; `env`'s `-i`, `-u`, `-v`, `-0`, `--debug`, `--list-signal-handling`, `-` and `--` in their documented spellings, `--default-signal`, `--ignore-signal` and `--block-signal` with a value only after `=`, its one-letter options read as getopt reads them, so several may share one word and the last of them may carry its value, `-iu HOME` and `-iuHOME` among them ([getopt](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap12.html)), each `-u` naming a variable that is not empty and holds no `=`, as GNU env requires before it runs anything, and the `name=value` words after them, then the command it runs, and its `-S` and `--split-string`, whose value, where it writes no quote, `\`, `$` or `#` and no `-C` or `--chdir` stands before it, env splits at blanks and puts in the option's place, before its later words, reading its options again from the first of them, so `env -S'node --no-warnings' lint` runs `node --no-warnings lint` and `env -S '-i node' lint` runs `node lint` ([env.c](https://github.com/coreutils/coreutils/blob/master/src/env.c), parse_split_string); `cross-env`'s `NAME=value` words, then the command it runs, and the options of `c8`, `nyc`, `env-cmd`, `dotenv` and `dotenvx run`, each as it documents them, then the command it runs, which `dotenv`, where a `--` stands, and `dotenvx run` take after the `--` only ([c8](https://github.com/bcoe/c8#cli-options), [nyc](https://github.com/istanbuljs/nyc#usage), [env-cmd](https://github.com/toddbluhm/env-cmd#-help), [dotenv-cli](https://github.com/entropitor/dotenv-cli#usage), [dotenvx](https://dotenvx.com/docs/advanced/run)), a dynamic word whose text before its first dynamic part is such a word's start, `NAME=$X` among them, being one too; A command with any other option before its operands, with a dynamic word where its reader needs a value, or whose program word has no reader, is not understood. The directory a command runs in is moved only by a shell builtin that its string's own shell runs, never by a program a launcher runs: `cd` with one static operand that does not start with `-`, and `pushd` with one that starts with neither `-` nor `+`, move it to that directory, read against the one before, and such a `cd` is taken to succeed, while such a `pushd` may instead fail and leave it where it was; `exit`, whatever its operands, and `exec` with a static first operand that does not start with `-` end it, so no later command of the string runs in it; any other `cd` or `pushd`, an `exec` whose first operand is dynamic or starts with `-`, `popd`, `return`, `.`, `source`, `eval`, a `command` or `builtin` whose later words name one of these or are dynamic, a command whose program word is dynamic, and a compound command other than `( )`, `[[ ]]`, `(( ))` and `coproc`, or a function definition, that is the only member of its pipeline move it to a directory the analysis does not know. A pipeline of more than one member runs each member in a subshell, whatever each member is, so it moves and ends nothing, and an and-or list that `&` sends to the background runs in a subshell, so what it moves reaches the later pipelines of its own list and no later list. In an and-or list a pipeline after `&&` runs where the one before it succeeded and one after `||` where it failed, so a pipeline runs in a known directory only where every way its list may reach it leaves the shell in that one directory, and a list starts where every way the list before it may end leaves it: `false && cd srv; node index.js` runs `index.js` in no directory the analysis knows, while `cd x || exit 1; node a.js` runs `a.js` in `x`, `pushd x || node b.js` runs `b.js` where the string runs, and `exit 0 && node a.js; node b.js` runs neither. The first two layers read no command that runs in a directory the analysis does not know or after its shell has ended, but the words of every simple command of the string's own line are read in the string's directory as well, wherever and whether it runs, for the roots, the uses and the configuration files below. The third layer reads the words of the held text below: every word of the string, whatever the first two layers read of it, and beside the strings each value of each file they are read from that is no command string, a workflow file, a git hook, a hook manager file and a makefile of `roots.15` to `roots.17` and nodemon's configuration, its `nodemonConfig` member and its `nodemon.json`. The held text of command strings, which the dependency rule below reads, is all of their text with the whole text of each of those files. The first two layers only add the roots, the uses and the runtime they read, and never take out of the hold a file the text names. A static word of a simple command that holds no `*`, read against the command's directory, roots each file of the program it names, directly or through the emit mappings that read an output file back to its source. The file a read command runs, read against the command's directory as written, and each module it loads before it that is written as a path, read against that directory as `require` reads it for `-r` and `--require`, as written, and as an ECMAScript module URL for `--import`, `--loader` and `--experimental-loader`, a relative one or a `file:` URL with its query and fragment removed and its percent escapes decoded, as [Node](https://nodejs.org/api/esm.html#urls) resolves it, each also with one of the extensions `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs` added and as the `index` file with one of them in the directory it names, roots each file of the program it names. A simple command of a manifest's command strings names a configuration file only by an option its program's tool documents for naming one, each the next word after it, or the text after `=` for `--config`, before any `--`: the `-c` and `--config` of [`eslint`](https://eslint.org/docs/latest/use/command-line-interface), [`stylelint`](https://stylelint.io/user-guide/cli), [`jest`](https://jestjs.io/docs/cli), [`vitest`](https://vitest.dev/guide/cli), [`vite`](https://vite.dev/guide/cli) and [`webpack`](https://webpack.js.org/api/cli/), and the `--config` of [`prettier`](https://prettier.io/docs/cli) and [`mocha`](https://mochajs.org/#command-line-usage), and also the value of `npx`'s `-c` before its first operand, a command line read as a configuration file's name as well. A dynamic or empty value names none, and no option of any other program names one, so `node -c scripts/check.js`, which checks the script's syntax, names no configuration file, and a file such an option takes is held as the words below hold it. Such a configuration file is read against the directory of its simple command and against the string's directory, and so is one that the command a simple command's reading ends on, after every launcher has handed its command on, names, read against that command's directory: where the file is a JSON file, or a module whose name ends with `.js`, `.mjs`, `.cjs`, `.ts`, `.mts` or `.cts`, below the target root, in no `node_modules` directory, it is read as a configuration file beside the manifest is, whatever its name. A path the first two layers name in a command string of a manifest, read against the command's directory, that names a file whose name ends with `.js`, `.mjs` or `.cjs`, below the target root, in no `node_modules` directory and held by no program, starts the configuration-file chain at that file, read against that manifest: its strings, and those of each file it imports, re-exports or loads by a relative specifier, are read as a configuration file's are. Such a path of a workflow step, a git hook or a recipe line starts the chain read against the target root's manifest. The words of a package's command strings, a manifest's against its directory, with the values of nodemon's configuration, and the target root's workflow steps, git hooks and recipe lines, with the values of each workflow file, hook manager file and makefile, against the target root, name files: a file of the program below the package's directory is named where one of its names appears in one of those words as a path. The words are the shell's. The first layer's parser reads each command string into words wherever its structure writes one: the program word and each argument word of a simple command, an assignment's value, a redirection's target, the words a `for`, a `select` and a `case` read and a test's operands, each word a parameter expansion's operation holds, and each word of the command line a command substitution or a process substitution runs, read the same way. A callee is a name of `require` where it is written as the name `require` or as a member named `require`, such as `module.require`, where an import, a re-export or a destructuring that carries it to its declaration names it `require`, or where it resolves to a variable of the target whose initializer is such a name or a call of a name of `createRequire`, read the same way, such as `const load = createRequire(import.meta.url)` ([Node `createRequire`](https://nodejs.org/api/module.html#modulecreaterequirefilename)), through as many such variables as hold it in turn. The analysis proves a callee the target's own where its type checker resolves it, through every import and re-export that carries it, to a function or a class the target writes with a body: a function or method declaration with a body, a class declaration, or a variable, a property or a class field whose initializer is a function, an arrow function or a class expression, in a file of the target, in no declaration file and under no `declare` modifier. A call through a callee proven the target's own loads nothing, roots nothing and is no load by a computed path, whatever its name, so a `createRequire` the target writes returns no `require`. Nothing else proves a callee the target's own, so a call of a name of `require` loads where the target declares it only ambiently, which only types it, where a parameter receives it, such as an AMD callback's, where the analysis cannot resolve the name, as for `module.require` with nothing declaring `module`, and wherever a reader without a type checker reads the call, as `conventions.3` reads one.

## Type-query aliases

**roots.24** An ambient global declaration in a declaration file whose type is `typeof import(<string>)[<string>]`, or `typeof import(<string>).<name>`, is an alias of the declaration that names the module the first string names exports under the second string or the name. A reference to the global is a reference to that declaration and to every link of the alias chain that reaches it, and the type query in the global's own declaration is not a reference. No finding is reported about the global declaration itself.

## Go packages no build links

**roots.25** In an application, a Go package of the target that no build the run sees links is dead with every declaration it holds: no main package, test, program or consumer the run loads imports it, directly or through other packages, and the run read its module whole. Such a package's `init` functions and blank declarations run only when the package is linked, so neither is a root there. A run that declares no consumer classes every declaration of such a package outside an `internal` tree `possible`, because outside programs may import the package, and one under an `internal` tree `certain`; a run that declares consumers has named the outside programs, so its classes are those of any other declaration. A file finding about such a package keeps its class.

## Go generators

**roots.26** A `//go:generate` directive names the inputs of the generator it runs, the program its first word names or the program `go run` or `go tool` names after it, by its base name and without a version. For `stringer` and `enumer` the inputs are the types its `-type` flag lists, in the directive's own package. For `mockgen` they are every interface the file its `-source` flag names declares, read against the directive's directory, or, in package mode, the comma-separated names of its last argument in the package its second-to-last argument names, `.` naming the directive's own package. The directive's words are the ones `go generate` splits it into, a double-quoted string being one word, and `$GOFILE` and `$GOPACKAGE` expand in each word. A flag written without `=` takes the next word as its value unless that word is a flag, or the flag is one of the generator's boolean flags. Every input is a root, and so is every method an input interface declares, because deleting either breaks `go generate`. A directive that passes a package directory by a relative path, `./` or `../` followed by the path, other than the directive's own directory, as a positional argument of the `generate` subcommand of `ent` or `entc`, which load that package and read its declarations by their names ([ent code generation](https://entgo.io/docs/code-gen)), has every exported declaration of that package outside its test files, whose every container is exported, as an input, a type parameter excepted. Any other program's relative path names no input, because it may as well be where the program writes. Each such input is a root.

**roots.27** A function named `Fuzz`, or `Fuzz` followed by a name that does not open with a lower-case letter, of type `func([]byte) int`, in a file whose build constraint holds with the `gofuzz` tag set for some setting of the other tags it names, a file with no build constraint included, is a root, because go-fuzz and the fuzzers that build its entry points by name, which set no tag, call it.

**roots.28** A declaration whose doc comment holds a line that opens with `swagger:` is a root, and so is every field of a struct type it declares, an anonymous struct's fields included, because the go-swagger generator reads each one.

**roots.29** A function or a method whose doc comment holds a line that opens with the swag annotation `@Router` followed by a space or a tab, in a line comment or a block comment, is a root, because swag reads the API operation the comment documents from the declaration whatever calls it.
