# Roots

Rules `roots.1` to `roots.29` of [the analysis](../analysis.md). A rule is cited by its id, which is never reused for another rule.

**roots.1** A root is live without a reference. Beside the roots `roots.patterns` and `ts.entry_files` configure, the entry points a manifest names and a library's published API, the TypeScript analysis marks the roots below, and the Go analysis those of the subsections whose title names Go. A root that names a file roots the file's top level and everything its export table names, a re-export walked to the declaration it carries, and is live under both liveness relations, because a program the project runs loads it.

## Configuration files by name

**roots.2** A file in the directory of a `package.json` the analysis reads, below the target root and in no `node_modules` directory, is a configuration file when its name is `<stem>.config.<ext>` or `<stem>.<qualifier>.config.<ext>`, with `<ext>` one of `js`, `mjs`, `cjs`, `ts`, `mts` and `cts`, or `.<stem>rc.<ext>`, with `<ext>` one of `js`, `mjs` and `cjs`. `<stem>` and `<qualifier>` are each a run of letters, digits, hyphens and underscores. A configuration file in the program is a root. A configuration file no program holds is read all the same, with no type information and no declaration of it judged: its strings are read under the rule below, the specifier of each of its imports and re-exports among them, so an import naming a dependency is a use of the dependency. A file such a file imports by a relative specifier, that no program holds either, is read the same way, and so on until no further file joins. A file outside the target root, or below a `node_modules` directory, is not a file of the project the analysis reads, so no such chain reads it: a relative specifier that reaches one adds no file. Such a relative specifier resolves against the importing file's directory to the first of these paths that names a file:

1. **roots.3** The path the specifier names, where its name ends with one of the extensions of step 3.
2. **roots.4** That path with a final `.js` replaced by `.ts` and then by `.tsx`, a final `.jsx` replaced by `.tsx` and then by `.ts`, a final `.mjs` replaced by `.mts`, or a final `.cjs` replaced by `.cts`.
3. **roots.5** That path with `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs` appended, in that order.
4. **roots.6** Where the path names a directory, the file `index` in that directory with the extensions of the previous step appended, in the same order.

**roots.7** A specifier that reaches no file adds no file and raises no setup failure. A specifier that names a file of another kind, a `package.json` or another JSON file among them, reaches no file, so the strings of a manifest a configuration file imports use none of the dependencies it declares.

**roots.8** A JSON configuration file is a file in the directory of a `package.json` the analysis reads, below the target root and in no `node_modules` directory, whose name is `<stem>.config.json`, `<stem>.<qualifier>.config.json`, `.<stem>rc` or `.<stem>rc.json`. It holds no declaration and is read for its strings alone.

## Strings in configuration

**roots.9** In a configuration file and in a JSON configuration file, every string literal and every template literal with no substitution, at any depth, is read against the `package.json` of the configuration file's directory, which for a file a chain of relative imports reaches is the directory of each configuration file whose chain reaches it, and against the file's own directory:

- **roots.10** A string equal to the name of a dependency that manifest declares, or to that name followed by `/` and a subpath, is a use of the dependency.
- **roots.11** A string that names, read against the file's directory, a source file of the program, directly or with one of the extensions the program's module resolution tries, roots that file, whether or not it starts with `./` or `../`. A string that starts with `/` or holds one of the glob characters `*`, `?`, `[` and `{` names no file.

**roots.12** A JSON object member's name is not read as a string. A string at a selection key of an applied convention row roots no file, as the convention rows below state, and a string in the configuration of a tool no applied row describes is read by this rule alone.

## Script entries

**roots.13** Every command string the analysis reads is read in three layers, without running it, in the directory it runs in: each value of the `scripts` member of a `package.json` the analysis reads and the `exec` command of nodemon's configuration, in the manifest's `nodemonConfig` member or in the `nodemon.json` beside it, in the manifest's directory, and each command string of a workflow step, a git hook and a makefile recipe line, in the directory `roots.15` to `roots.17` give it, or in one the analysis does not know where `roots.15` says so. The first layer parses the string as a POSIX shell command line, with a shell parser rather than by splitting it at characters, into its simple commands, each a program word and its argument words, joined by `&&`, `||`, `;`, `|`, `&` and newlines, with quotes, backslash escapes, line continuations and comments read as the shell reads them. A word that holds a parameter expansion, a command substitution, an arithmetic expansion, a process substitution, one of the glob characters `*`, `?` and `[` outside quotes, a brace expansion or a leading `~` outside quotes is dynamic: its value is not known. An assignment written before a program word, a redirection, a here-document, a compound command, a function definition and a command with no program word are not read as words, and a string any part of which does not parse is read as no command at all. The second layer reads each simple command whose program word is the name of a tool it has a reader for, or a path ending `node_modules/.bin/` followed by such a name, by that tool's reader, which reads only the options the tool documents for choosing the file it runs, a module it loads before that file, or the command it runs: `node`'s `-r`, `--require`, `--import`, `--loader` and `--experimental-loader`, each with its value as the next word or, for a long option, after `=`, with its first operand as the file it runs, which it runs under Node; `tsx`'s `-r`, `--require` and `--import`, after an optional `watch`, and `ts-node`'s `-r`, `--require` and `--esm`, each with its first operand as the file it runs; `env`'s `-i`, `-u`, `-v`, `--debug`, `-` and `--` in their documented spellings, each `-u` naming a variable that is not empty and holds no `=`, as GNU env requires before it runs anything, and the `name=value` words after them, then the command it runs, and `cross-env`'s `NAME=value` words, then the command it runs; `npx`'s and `npm exec`'s or `npm x`'s `--package`, `npx`'s `-p`, `--yes`, `-y`, `--no` and `--`, then the command it runs, the first operand's name without a version where no `--package` names the package, and `-c` or `--call`, whose value is read as a command string of its own in the same directory, where no operand follows; `npm exec` reads an option after its first operand too, so one written there and no `--` before it is not understood; `pnpm exec` and `pnpm dlx` with `--package`, `yarn dlx` with `-p`, `--package`, `-q` and `--quiet`, and `bunx` with `-p` and `--package`, each then the command it runs, and `yarn node`, which runs `node`; and `npm run` and `npm run-script` with a script's name, which runs another script of the same manifest, read on its own. A command with any other option before its operands, with a dynamic word where its reader needs a value, or whose program word has no reader, is not understood. The directory a command runs in is moved only by a shell builtin that its string's own shell runs, never by a program a launcher runs: `cd` with one static operand that does not start with `-`, and `pushd` with one that starts with neither `-` nor `+`, move it to that directory, read against the one before, and such a `cd` is taken to succeed, while such a `pushd` may instead fail and leave it where it was; `exit`, whatever its operands, and `exec` with a static first operand that does not start with `-` end it, so no later command of the string runs in it; any other `cd` or `pushd`, an `exec` whose first operand is dynamic or starts with `-`, `popd`, `return`, `.`, `source`, `eval`, a `command` or `builtin` whose later words name one of these or are dynamic, a command whose program word is dynamic, and a compound command other than `( )`, `[[ ]]`, `(( ))` and `coproc`, or a function definition, that is the only member of its pipeline move it to a directory the analysis does not know. A pipeline of more than one member runs each member in a subshell, whatever each member is, so it moves and ends nothing, and an and-or list that `&` sends to the background runs in a subshell, so what it moves reaches the later pipelines of its own list and no later list. In an and-or list a pipeline after `&&` runs where the one before it succeeded and one after `||` where it failed, so a pipeline runs in a known directory only where every way its list may reach it leaves the shell in that one directory, and a list starts where every way the list before it may end leaves it: `false && cd srv; node index.js` runs `index.js` in no directory the analysis knows, while `cd x || exit 1; node a.js` runs `a.js` in `x`, `pushd x || node b.js` runs `b.js` where the string runs, and `exit 0 && node a.js; node b.js` runs neither. The first two layers read no command that runs in a directory the analysis does not know or after its shell has ended, but the words of every simple command of the string's own line are read in the string's directory as well, wherever and whether it runs, for the roots, the uses and the configuration files below. The third layer is held text, read as plain text below: all of the string's text, whatever the first two layers read of it, and beside the strings the whole text of each file they are read from, a workflow file, a git hook, a hook manager file and a makefile of `roots.15` to `roots.17` and nodemon's configuration, its `nodemonConfig` member and its `nodemon.json`, so a part of such a file that no command string is read from, a comment among them, or that the reading of its structure misses, still holds what it names. The first two layers only add the roots, the uses and the runtime they read, and never take out of the hold a file the text names. A static word of a simple command that holds no `*`, read against the command's directory, roots each file of the program it names, directly or through the emit mappings that read an output file back to its source. The file a read command runs, read against the command's directory as written, and each module it loads before it that is written as a path, read against that directory as `require` reads it for `-r` and `--require`, as written, and as an ECMAScript module URL for `--import`, `--loader` and `--experimental-loader`, a relative one or a `file:` URL with its query and fragment removed and its percent escapes decoded, as [Node](https://nodejs.org/api/esm.html#urls) resolves it, each also with one of the extensions `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs` added and as the `index` file with one of them in the directory it names, roots each file of the program it names. A command loading a module written with a URL scheme `require` does not read, or with any scheme but `file:` as an ECMAScript module, or as a URL that does not decode, encodes a `/` or a `\` or names a host, is not understood. A module a read command loads before the file it runs that is written as a bare module specifier is a use of the dependency it names, read as an import's specifier is, so `node --loader ts-node/esm main.ts` uses `ts-node`, and a word handed to the program loads nothing, so `node main.js --require x` uses no `x` through this sentence. A static word of a command of a manifest's command strings equal to the name of a command that the installed manifest of a dependency the manifest declares names in its `bin`, the package's own name without its scope where `bin` is a string, is a use of that dependency, and such a word of a workflow step, a git hook or a recipe line is a use of such a dependency of any manifest the analysis reads. A dependency of the manifest whose name, or the name of a command its installed manifest names in its `bin`, appears in the held text of the manifest's command strings or of the target root's workflow steps, git hooks and recipe lines, with none of a letter, a digit, `_`, `.`, `@` and `-` before it and none of a letter, a digit, `_` and `-` after it, is a use of that dependency, because a command may run or load it in a way the first two layers do not read. A simple command of a manifest's command strings names a configuration file only by an option its program's tool documents for naming one, each the next word after it, or the text after `=` for `--config`, before any `--`: the `-c` and `--config` of [`eslint`](https://eslint.org/docs/latest/use/command-line-interface), [`stylelint`](https://stylelint.io/user-guide/cli), [`jest`](https://jestjs.io/docs/cli), [`vitest`](https://vitest.dev/guide/cli), [`vite`](https://vite.dev/guide/cli) and [`webpack`](https://webpack.js.org/api/cli/), and the `--config` of [`prettier`](https://prettier.io/docs/cli) and [`mocha`](https://mochajs.org/#command-line-usage), and also the value of `npx`'s `-c` before its first operand, a command line read as a configuration file's name as well. A dynamic or empty value names none, and no option of any other program names one, so `node -c scripts/check.js`, which checks the script's syntax, names no configuration file, and a file such an option takes is held as the held text below holds it. Such a configuration file is read against the directory of its simple command and against the string's directory, and so is one that the command a simple command's reading ends on, after every launcher has handed its command on, names, read against that command's directory: where the file is a JSON file, or a module whose name ends with `.js`, `.mjs`, `.cjs`, `.ts`, `.mts` or `.cts`, below the target root, in no `node_modules` directory, it is read as a configuration file beside the manifest is, whatever its name. A path the first two layers name in a command string of a manifest, read against the command's directory, that names a file whose name ends with `.js`, `.mjs` or `.cjs`, below the target root, in no `node_modules` directory and held by no program, starts the configuration-file chain at that file, read against that manifest: its strings, and those of each file it imports, re-exports or loads by a relative specifier, are read as a configuration file's are. Such a path of a workflow step, a git hook or a recipe line starts the chain read against the target root's manifest. The held text of a package's command strings, a manifest's against its directory, with the whole text of nodemon's configuration, and the target root's workflow steps, git hooks and recipe lines, each with the directory a step or a lefthook command is written to run in, with the whole text of each workflow file, git hook, hook manager file and makefile, against the target root, names files as plain text: a file of the program below the package's directory is named where one of its names appears anywhere in that text. A file's names are, for each path it has, its own and each one the emit mappings read back to it, the path's last segment without the extension `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` or `.cjs`, or `.d.ts`, `.d.mts` or `.d.cts`, or the whole segment where it is that extension alone, and for a file whose name without it is `index` also the last segment of its directory, where it has one, and `.` too where that directory is the package's. No name is empty, because an empty name appears in every text. Every spelling of the file's path relative to the package's directory, with or without a leading `./`, with `/` or `\` between segments, with or without its extension or its `/index` part, and every longer path that ends in one, holds one of those names, so a file the held text names is never missed; a file it does not name may be held too. A file the held text names is held unless a root enters it with every name it exports, because a command can use no more of such a file than that root keeps live. Holding a named file keeps its exports; it never keeps a declaration that is unexported and unreferenced. The file itself, which reaches its top level, and each declaration its export table names are held as an unanswered question holds a declaration in `program.33`, so no finding about the file itself or a name it exports is reported, while every other finding about the file, a declaration it neither exports nor references and an unused member of a declaration it exports among them, is reported as it is in a file a root enters with every name it exports. Each configuration in which the held text of one package holds such a file counts that package as one question in `unanswered_questions`, and the report carries one `unread-command` note, which `notes.7` defines, for the package, whichever of its command strings name its files.

**roots.14** A module a path the first two layers of `roots.13` name in a script entry names, read against the directory its command runs in, below the target root and in no `node_modules` directory, whether a program holds it or not, is a build script, read without running it. In a build script, each call the script runs, written at its top level or in a function that a call it runs calls or passes as an argument, of a bundler's build function, `build`, `buildSync` or `context` imported from `esbuild`, the value `webpack` exports, or `rollup` or `watch` imported from `rollup`, by a named import, a default or namespace import, a top-level `require` binding or a direct `require(...)` call, and named by no parameter or local binding of a function it runs in, names its entries in the first argument's entries option, `entryPoints`, `entry` and `input` respectively, written as an object literal or as a top-level `const` binding to one. An entry is a string literal or a template literal with no substitution, an element of an array of them, a value of an object of them, the `in` member of an esbuild entry object or the `import` member of a webpack entry descriptor, or a `resolve` or `join` call whose first argument is `__dirname` or `import.meta.dirname` and whose other arguments are such literals. A literal entry is read against the directory the option that moves the working directory sets, esbuild's `absWorkingDir` and webpack's `context`, else against the manifest's directory, where the script runs, and a call entry against the script's own directory. Each source file of the program an entry names, directly or with one of the extensions the program's module resolution tries, roots that file and what it exports, and an esbuild entry holding a glob character roots every such file the glob matches. In a library what such a file exports is published API as well, because the bundle hands it to every program that loads it. A webpack entry that is neither relative nor absolute is a module request and names no file. A value that is not written out, a computed path or an options object built at run time among them, names nothing.

## Workflow steps

**roots.15** A workflow file is a file whose name ends with `.yml` or `.yaml` in the directory `.github/workflows` of the target root. It is read as a [YAML 1.2](https://yaml.org/spec/1.2.2/) document: block and flow mappings and sequences, plain, single-quoted, double-quoted and block scalars, decoded as YAML decodes them, with their escapes, line folding, indentation and chomping, inside a flow collection over several lines too, anchors and the aliases that name them, and comments, wherever a comment line stands between a key and its value. A document written with anything else, a tag, a complex key, an anchor on a key, an alias of no anchor, a second document, a tab in an indentation or text YAML does not accept, or whose aliases, each expanded, would grow its value by more than 100,000 nodes and characters, is not read: no command string is read from it, and its whole text is held as `roots.13` states. Every mapping of the document, wherever it stands and however it is written, that has a `run` key whose value is a scalar that is not blank holds a run command, the scalar's value, a number or a boolean read as its text. The string runs in the directory the `working-directory` key of the same mapping names, else the one the `working-directory` key of the `run` mapping of the `defaults` mapping of the innermost mapping holding it names, the job's or the workflow's, each read against the target root, else the target root. A directory written with a `${{ }}` expression, which GitHub Actions evaluates, is one the analysis does not know. The string is read as `roots.13` reads a command string, so a word that names a source file of the program, read against that directory, roots that file, and a word equal to the name of a command that a dependency of a manifest the analysis reads declares is a use of that dependency.

**roots.16** A git hook is read as a workflow step's run command is: each file directly in the directories `.husky` and `.githooks` of the target root, read whole as one command string run in the target root, because each such file is a shell script, each command the `run` key of a mapping of `lefthook.yml`, `lefthook.yaml` or `.lefthook.yml` holds, run in the directory the `root` key of the same mapping names, read against the target root, as [lefthook](https://lefthook.dev/configuration/root/) runs it, else the target root, and each command the `entry` key of a mapping of `.pre-commit-config.yaml` holds, run in the target root, the last two files read as YAML documents as a workflow file is. The whole text of each of these files is held as `roots.13` states, so a comment of a git hook holds what it names, and a word of one roots a file and uses a dependency as a workflow step's word does.

**roots.17** The target root's makefile, the first of `GNUmakefile`, `makefile` and `Makefile` it holds, is read as text, its recipe lines its command strings: a line that starts with a tab, joined with each line a trailing `\` continues it onto, with its leading `@`, `-` and `+` removed. Make runs each recipe line in a shell of its own, so each is one command string, run in the target root and read as `roots.13` reads a command string, and a `cd` in it moves only the later commands of its own line.

## Manifest entries

**roots.18** Each entry point a `package.json` the analysis reads names, its `main`, `module`, `types`, `browser` and `bin`, every target of its `exports`, and each `./` path a `browser` object replaces a module with, the [browser field](https://github.com/defunctzombie/package-browser-field-spec) a bundler reads for a browser build, is read back to a source file of the program: the file the target names where the program holds it, else the file the emit mappings of the workspace rule above read it back to. A target neither reads back to is read against each configuration as if the manifest's directory were its output directory, back to the configuration's root directory, so `./index.js` of a package published from its build directory reads back to `<rootDir>/index.ts`. A target that names a file no program holds is read as a configuration file outside the program is, and each program file a relative specifier of its imports, its re-exports and its `require()` and `import()` calls with a literal names, read through the emit mappings, and so on through each file of that chain no program holds, is the entry point. A target that neither reads back to a source file is read back by name to the files the configuration-file, script-entry and HTML-entry rules of this section root. Its name is its path relative to the manifest's directory below its first directory, or the whole path where it names no directory, without its output extension, being `.d.ts`, `.d.mts`, `.d.cts`, `.js`, `.mjs`, `.cjs` or `.jsx`. A rooted file of the manifest's own package, no `package.json` between them, whose path relative to the manifest's directory, without its source extension, ends with that name at a directory boundary is the entry point, so `dist/cli/main.js` reads back to a rooted `src/cli/main.ts`. Every file that matches is the entry point, for the roots and for a library's published API alike, and a target that reads back to no file roots nothing.

## Release tags

**roots.19** In a library, a published workspace member of an application included, an exported TypeScript declaration whose documentation comment holds the release tag `@public`, `@beta` or `@alpha` is published API, as a declaration a manifest entry reaches is, and so is each public member of a type it declares. Its documentation comment is the last `/** */` comment before it with only white space between the two. A tag is written as `@` and its name, after white space or the comment's opening and before white space or the comment's end. Such a declaration is live under reachability alone, as the published API is, and a finding about it carries the reachability class the confidence rule below gives the published API. That class is `possible` when the run holds no consumer information, `probable` when a declared consumer did not load, and `certain` when every declared consumer loads, so a tagged declaration no loaded consumer uses is reported at `certain`. Elsewhere in an application the tags mark nothing, because an application has no published API outside its published workspace members.

## HTML entry files

**roots.20** A file whose name ends with `.html`, below the target root and in no `node_modules` directory, is an HTML entry file, read as text as a component file is, with no markup parsed. A `<script` start tag whose `type` attribute is `module` begins a module script, and one inside an HTML comment begins one too, because no markup is parsed. A module script with a `src` attribute roots the file `src` names, and so does a classic script, one whose start tag carries a `src` attribute and either no `type` attribute or a `type` of `text/javascript` or `application/javascript`, because the page runs the file either way. One without roots each file that a specifier starting with `/`, `./` or `../` names, of an import or a re-export declaration in its content up to the next `</script>` end tag. An attribute is written `name="value"`, `name='value'` or `name=value`, and its name compares without regard to case. A value or a specifier that starts with `//` or with a scheme and a colon, `https:` among them, names no file. One that starts with a single `/` is read against the directory of the nearest `package.json` at or above the HTML file, and any other against the HTML file's own directory. Either resolves as a relative specifier of a configuration file does. A value or a specifier that names no source file of the program is read back through the emit mappings of the workspace rule above, applied to every configuration of the run: an output file of a configuration's output directory or declaration directory maps to the source file of the same name below its root directory, so a page that loads compiled output roots the source that emits it. A value that starts with a single `/` is read as well against each configuration's output directory whose top holds the HTML file, because a server whose root is that directory serves the page. One that reads back to no source file roots nothing. A file a script element roots is a root as an entry of `ts.entry_files` is.

## Markdown and MDX documents

**roots.21** A file whose name ends with `.md` or `.mdx`, below the target root and in no `node_modules` directory, is read as text: a line outside a fenced code block that starts with an import declaration roots the source file its relative specifier names, on disk or through the emit mappings, as an MDX compiler hoists the import into the module it builds, and with it the exports the import reads: `default` for a default binding, each name its braces list, every export for a namespace import or a clause this reading does not parse, and none for an import written for its effects alone. A file a document imports is an entry file for `DS1503` only for the exports the import reads, so another export of it that only its own file references is reported under that code.

## Computed loads

**roots.22** An `import()` or `require()` call whose argument is a template literal or a concatenation whose leading literal part is a relative specifier ending in `/` roots every source file below the directory it names, read against the calling file's directory, with each file's export table, as a bundler's context module loads them; a leading part naming the calling file's own directory, or a directory that holds it, roots nothing, because it would name every sibling. An `import.meta.glob` call whose argument is a relative string literal glob, or an array of them, roots every source file the glob matches against the calling file's directory, with its export table.

**roots.23** A call of a function named `require` whose name resolves to a declaration in a file of the target is a call of the target's own function: it loads nothing, roots nothing and is no load by a computed path.

## Type-query aliases

**roots.24** An ambient global declaration in a declaration file whose type is `typeof import(<string>)[<string>]`, or `typeof import(<string>).<name>`, is an alias of the declaration that names the module the first string names exports under the second string or the name. A reference to the global is a reference to that declaration and to every link of the alias chain that reaches it, and the type query in the global's own declaration is not a reference. No finding is reported about the global declaration itself.

## Go packages no build links

**roots.25** In an application, a Go package of the target that no build the run sees links is dead with every declaration it holds: no main package, test, program or consumer the run loads imports it, directly or through other packages, and the run read its module whole. Such a package's `init` functions and blank declarations run only when the package is linked, so neither is a root there. A run that declares no consumer classes every declaration of such a package outside an `internal` tree `possible`, because outside programs may import the package, and one under an `internal` tree `certain`; a run that declares consumers has named the outside programs, so its classes are those of any other declaration. A file finding about such a package keeps its class.

## Go generators

**roots.26** A `//go:generate` directive names the inputs of the generator it runs, the program its first word names or the program `go run` or `go tool` names after it, by its base name and without a version. For `stringer` and `enumer` the inputs are the types its `-type` flag lists, in the directive's own package. For `mockgen` they are every interface the file its `-source` flag names declares, read against the directive's directory, or, in package mode, the comma-separated names of its last argument in the package its second-to-last argument names, `.` naming the directive's own package. The directive's words are the ones `go generate` splits it into, a double-quoted string being one word, and `$GOFILE` and `$GOPACKAGE` expand in each word. A flag written without `=` takes the next word as its value unless that word is a flag, or the flag is one of the generator's boolean flags. Every input is a root, and so is every method an input interface declares, because deleting either breaks `go generate`. A directive that passes a package directory by a relative path, `./` or `../` followed by the path, other than the directive's own directory, as a positional argument of the `generate` subcommand of `ent` or `entc`, which load that package and read its declarations by their names ([ent code generation](https://entgo.io/docs/code-gen)), has every exported declaration of that package outside its test files, whose every container is exported, as an input, a type parameter excepted. Any other program's relative path names no input, because it may as well be where the program writes. Each such input is a root.

**roots.27** A function named `Fuzz`, or `Fuzz` followed by a name that does not open with a lower-case letter, of type `func([]byte) int`, in a file whose build constraint holds with the `gofuzz` tag set for some setting of the other tags it names, a file with no build constraint included, is a root, because go-fuzz and the fuzzers that build its entry points by name, which set no tag, call it.

**roots.28** A declaration whose doc comment holds a line that opens with `swagger:` is a root, and so is every field of a struct type it declares, an anonymous struct's fields included, because the go-swagger generator reads each one.

**roots.29** A function or a method whose doc comment holds a line that opens with the swag annotation `@Router` followed by a space or a tab, in a line comment or a block comment, is a root, because swag reads the API operation the comment documents from the declaration whatever calls it.
