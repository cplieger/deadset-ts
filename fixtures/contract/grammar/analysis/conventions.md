# Convention rows

Rules `conventions.1` to `conventions.14` of [the analysis](../analysis.md). A rule is cited by its id, which is never reused for another rule.

**conventions.1** An analyzer may carry a table of convention rows, each the data of one framework's file-system conventions. A row has a name, an enabling package, a version range in the semantic-versioning range syntax, the globs of its entry files, the globs of the files it excludes, the directories its framework generates, the configuration properties that move a directory those globs or a generated directory name, each with the configuration files the property is read from and, for a property that is an option of a call, the module and the exported name of the function called, the configuration properties whose value names a package by a short name, each with the configuration files it is read from and the package name the value stands for, written with `{}` where the value goes, the selection keys, the configuration properties whose value only selects files to test, to mutate, to cover or to ignore, each with the configuration files it is read from, the package keys, the members of a configuration file whose strings name the packages its tool loads, each with the configuration files it is read from, the manifest keys, the members of a `package.json` its tool reads its configuration from, the manifest entry keys, the members of that `package.json` whose strings name the tool's entries, each naming a directory of entries or one entry, the prefixed-name properties, the configuration properties whose value names a package by its tool's prefix convention, each with the configuration files it is read from, the prefix and the marker a value starts with, if any, the test-file properties, the configuration properties whose value names a file the tool's test runner loads beside the tests, each with the configuration files it is read from and the properties its paths resolve against, and the test directories, each with the configuration files it is read from, the property naming a directory of tests, the property naming the patterns of the test files below it, the pattern that holds where no object names one, and the property listing the projects that each name their own, and the test runner, the reader of the files the row's runner runs as tests, which `conventions.14` states. The table is part of the analyzer, versioned with it, and no configuration key adds a row.

**conventions.2** A row applies when a `package.json` the analysis reads declares the enabling package as a dependency, a development dependency, a peer dependency or an optional dependency, and the version the installed package's own `package.json` names, found from that manifest's directory as the compiler resolves a package, is in the row's range. An enabling package declared as a dependency or a development dependency whose installed manifest the analysis cannot find is the setup failure `missing-module`, except in a nested package's manifest, where it applies no row and raises no setup failure, because no run requires a nested package to be installed. An enabling package declared only as a peer dependency or an optional dependency whose installed manifest the analysis cannot find applies no row and raises no setup failure. An applied row's globs are matched against the directory of the manifest that declared the package, each against a source file's own path and against each output path the emit mappings of the configuration holding the file write it to, so a glob naming build output names the source that output is compiled from: every file an entry glob matches and no exclude glob matches is a root, as an entry of `ts.entry_files` is, and every file below a directory the row names as generated, read against the same directory, is a generated file, whose declarations the `generated-file` class of [`exemptions.json`](../../exemptions.json) retains. A generated directory a configuration property moves is read where the property sets it, as an entry glob's directory is, so a code generator whose configuration names its output directory, a CSS-in-JS tool's `outdir` among them, is described by a row whose only content is that generated directory.

**conventions.3** A property that moves a directory is read from the row's configuration file without running it, in the objects the row reads there, under the one reading of a module that every rule of this page and `roots.14` use. Where the property is not an option of a call, the object is the file's default export, in each of its forms: the expression `export default` or `export =` writes, the binding an `export { name as default }` specifier names, the document of a JSON configuration file, and, in a file that writes no `import` or `export` declaration and declares neither `module` nor `exports`, the value Node leaves in `module.exports` once the file's top level has run. That value is the one the file's last top-level assignment of `module.exports` writes, `exports = module.exports = value` and `module.exports = exports = value` among them, with the members each later top-level assignment of a member of `module.exports`, or of `exports` while it still holds the module's value, adds; a top-level write of the module's value this reading does not model, a compound assignment or a call that may set a member among them, may set any member, as a spread may. A default export that is a function or a class holds no object. A configuration file whose name ends with `.yml` or `.yaml` is read as the JSON value its YAML document denotes, in the subset tool configurations write: block and flow mappings and sequences, and plain, single-quoted and double-quoted scalars, a plain scalar read under the YAML core schema, with comments. A document that uses anything else, an anchor, an alias, a tag, a block scalar, a complex key or a second document, holds no object to read, as a JSON document that does not parse holds none. No property that moves a directory is read from such a file, because a failure names a line of the file's text. A default export that names a top-level `const`, `let` or `var` binding the file assigns nowhere but in its initializer is read through to that initializer, and one that is a call, other than a `require()` call, is read through to every argument the call passes, each read through again, until an expression that is neither, so `mergeConfig(base, defineConfig({ test }))` is read in `base` and in `{ test }`. Where the property is an option of a call, the objects are the first arguments of every call in the file to the row's function through a binding of the row's module: by the function's exported name under any local name, as a member of the module's namespace, or, where the function is the module's default export, as the module's value; an argument that names such a top-level binding is read through to its initializer, and no further call is followed. The file binds the module by an `import` declaration, a named import binding the export it names, a namespace import the namespace, and a default import the module's value and its namespace both; by an import assignment `import name = require("<module>")`, binding what a default import binds; by a top-level `const`, `let` or `var` declaration whose initializer is a `require()` call with the row's module as its one argument, written as a string literal or a template literal with no substitution, an object binding pattern binding each exported name it lists under its local name, as a named import does, a name binding what a default import binds, and a name whose initializer reads one member of such a call binding that export; and by such a `require()` call itself, written where its value or a member of it is called. A `require()` call is one `roots.23` defines, read without a type checker, so no callee is proven the file's own and a call of the file's own `require` function is one too: the declaration a name resolves to is read by the file's scopes, so `load` is a name of `require` after `const load = createRequire(import.meta.url)` or `const load = Module.createRequire(__filename)`, and `make` one of `createRequire` after `const { createRequire: make } = require("module")`, through as many variables as hold it in turn. A name resolves through the scopes that enclose it, as ECMAScript declares names: a parameter, or a declaration of an enclosing function, block, `catch` clause or loop head, makes a call through the same name another call, and a name none of them declares, the file's top level included, is a global. Parentheses, `as`, `satisfies` and the non-null assertion are read through wherever an expression is. A call with no argument, and a file with no object to read, set nothing.

**conventions.4** The property is a path of keys through nested object literals, each key matching a property whose name is an identifier, a string literal or a template literal with no substitution, or a computed name whose expression is a string literal or a template literal with no substitution. Where the value at the end of the path is a string literal or a template literal with no substitution, the globs read each directory so set; where no object the row reads sets the property, the globs read the default directory. The row is the setup failure `convention-not-literal` where the value at the end of the path is anything else, a template literal with a substitution, a concatenation, a call and a name among them; where a value along the path is not written as an object literal, a name bound to an object literal among them, because a key's value is not read through a declaration; where the object the row reads is not written as an object literal, a default export that is a function or a class among them; and where the object the row reads or an object along the path holds a spread, or a computed name whose expression is not a string literal, a numeric literal or a template literal with no substitution, because either may set any key. An object the row does not read, the options of another function in the same file among them, sets nothing and raises no failure.

**conventions.5** A property that names a package by a short name is read from an applied row's configuration files as a property that moves a directory is, and a string value at the end of its path, or a string element of an array value there, stands for the package name the row writes with that string in place of `{}`. A declared dependency of that name is used. Where the value is not a literal, every declared dependency whose name the row's package name can produce with some value in place of `{}` is used, and the row raises no setup failure for the property. A string value equal to a declared dependency's own name is a use under the strings rule above whatever the row says.

**conventions.6** A prefixed-name property is read as a property that names a package by a short name is, and a string value at the end of its path, or a string element of an array value there, names a package by the prefix convention: a name `x` stands for `<prefix>-x`, a scope `@s` alone for `@s/<prefix>`, a scoped name `@s/x` for `@s/<prefix>-x`, and a name that already starts with `<prefix>-`, or a scoped name whose second part does, for itself. Where the property has a marker, only a value that starts with the marker names a package, its name the text between the marker and the value's last `/`, so `plugin:react/recommended` names `react`. Where it has none, a value holding a `:` or starting with `.` or `/` names none, and the name ends at the value's first `/` past a scope, so `airbnb/hooks` names `airbnb`. A declared dependency so named is used. A value that is not a literal uses nothing under this rule and raises no setup failure.

**conventions.7** A selection key is read from an applied row's configuration files as a property that moves a directory is. A string value at the end of its path, or a string element of an array value there, roots no file under the strings rule above, because the tool reads a file it selects only when another key runs or loads that file. A key that runs or loads a file is no selection key, so a string it holds roots the file it names. A selection key whose value is not a literal raises no setup failure, and every string the file holds elsewhere is read under the strings rule.

**conventions.8** A manifest entry key is read from the `package.json` that declared the row's enabling package, a key path whose `*` stands for every member of the object it reaches. Every string at any depth of the value there, a JSON object member's name excepted, read against that manifest's directory with leading `./` segments dropped, writes an entry glob: for a key naming a directory, every module below it, and a string holding a glob character names none; for a key naming an entry, the string itself and the string followed by a JavaScript or TypeScript extension. A string that leaves the manifest's directory writes none. The globs are matched as the row's own entry globs are, so a key naming build output roots the source the emit mappings read it back to.

**conventions.9** A manifest key is read from the `package.json` that declared the row's enabling package. Every string at any depth of that member's value, a JSON object member's name excepted, that equals the name of a dependency the manifest declares, or that name followed by `/` and a subpath, is a use of the dependency. A string under a member that no applied row names as a manifest key is no use of a dependency under this rule.

**conventions.10** A package key is read from each of an applied row's configuration files, in the objects the row reads there as it reads a property that moves a directory, the document of a file whose name ends with `.json` among them. Every string at any depth of the value of a member of that name, a JSON object member's name excepted, at any depth of those objects, that equals the name of a dependency the manifest that declared the row's enabling package declares, that name followed by `/` and a subpath, or that name followed by `:` and a name, is a use of the dependency, so a string `"@example/tool:build"` under a package key `builder` uses `@example/tool`. Such a string uses no other dependency itself, and a string under a member that no applied row names as a package key is no use of a dependency under this rule. A declared peer of a dependency it uses is needed as the precondition of `DS1701` in [`kinds.json`](../../kinds.json) states.

**conventions.11** A test-file property is read from an applied row's configuration files as a property that moves a directory is, a key `*` in its path standing for every element of an array and every member of an object it reaches, so a property can name the setup files of each project a configuration lists inline. Each string value at the end of its path, or string element of an array value there, read against the directory the row's resolving properties give in the object the path's last `*` reaches, or the configuration's own object for a path with none, or else the configuration file's own directory, names a test file, as a file `ts.test_files` names is one, because the runner loads the file only to run tests. Where a resolving property is set to anything but one string, the strings in its object name no file. A file a test-file property names is not rooted by the strings rule.

**conventions.12** The configuration's own keys win. A row `ts.disabled_conventions` names does not apply, adds no root and raises no setup failure, and the entries of `ts.entry_files` are roots whether a row applies or not. A row only adds roots, uses, retentions and test files. The report lists each row it applied in `conventions_applied`.

**conventions.13** A test directory is read from an applied row's configuration files, in each object the file's default export holds as `conventions.3` reads it. The object names a directory of tests, its directory property read against the configuration file's directory, and the patterns of its test files, its pattern property a string or an array of strings, the row's default pattern where the object sets none and the configuration file's directory where it sets no directory. Where the object's projects property lists objects, each listed object is read on its own, a property it does not set taken from the configuration's object, and the configuration's own directory and patterns name no test file beside them. Every file below a test directory that one of its patterns matches is a test file, as one `conventions.11` names is, a pattern matched as the row's test runner matches it: Playwright's reads a pattern that does not start with `**/` with `**/` before it and matches it against the file's whole path, without regard to case ([Playwright `testMatch`](https://playwright.dev/docs/api/class-testconfig#test-config-test-match)). An object whose directory, patterns or projects its text does not write out, a value that is no literal and a spread or a computed key that may set one among them, names no test file.

**conventions.14** A test runner reads the files its runner runs as tests, for each manifest that applies its row, from the runner's configuration and from each simple command of that manifest's `scripts` that runs it, read as `roots.13` reads a command, its first word naming the runner by its name or a path ending in it. Each file it names is a test file, as one `conventions.11` names is. A configuration is read as `conventions.3` reads a default export; a value the runner needs that is not written out as a literal, an option of a command the runner's table does not name, a dynamic word and a configuration that is no object literal among them, names no test file for that configuration or command, and raises no setup failure. A runner reads as its own source does:

- Mocha, versions 10 to 12 ([lib/cli](https://github.com/mochajs/mocha/tree/main/lib/cli)): one run in the manifest's directory with no operand, and one per command running `mocha` or `_mocha`. A run's configuration file is the one `--config` names, none where it writes `--no-config`, and otherwise the first of `.mocharc.cjs`, `.mocharc.js`, `.mocharc.mjs` from version 12, `.mocharc.yaml`, `.mocharc.yml`, `.mocharc.jsonc` and `.mocharc.json` in the nearest directory at or above the run's that holds one; the `mocha` member is read too, of the file the last `--package` names, read against the run's directory, or else, where none names one or the last names the empty string, of the nearest `package.json` at or above the run's directory, and of none where the last of `--package` and `--no-package` the command writes is `--no-package`, or where the nearest `package.json` cannot be read; a command whose `--package` file cannot be read, or whose `package.json` does not parse or parses to `null`, names no test file. The specs, the operands and `spec` values of the command line, the file and the member, are joined, `./test` where none is written, and so are `file`, `ignore` and `extension` values, the extensions `js`, `cjs` and `mjs` where none is written; the command line, then the file, then the member decides `recursive`. Each spec is read against the run's directory: an existing file is a test file; an existing directory names its own files, at any depth where `recursive` holds, with one of the extensions and a name not starting with `.`; a glob names the files it matches; any other spec names the file it names with an extension appended. A file an `ignore` glob matches is none, and each `file` value is a test file.
- Jest, versions 29 and 30 ([jest-config](https://github.com/jestjs/jest/tree/main/packages/jest-config)): the configuration of the manifest's directory, and of each directory or file a command running `jest` names by `--config` or `-c`, is the first of `jest.config.js`, `jest.config.ts`, `jest.config.mjs`, `jest.config.mts` from version 30, `jest.config.cjs`, `jest.config.cts` from version 30 and `jest.config.json` that it holds, else the file a string `jest` member of its `package.json` names, else that member's object, else the defaults; a directory holding both a file and the member is configured by neither. `rootDir` is read against the configuration's directory, the directory itself where unset, and `<rootDir>` in a path stands for it. Where `projects` lists projects, each listed object is read as a configuration of its own, and each listed string names the configuration files and directories its path or glob matches. Otherwise the test files are the files below each of `roots`, `<rootDir>` where unset, whose name ends with `.` and one of `moduleFileExtensions`, that a `testMatch` glob matches over the whole path, a glob starting `!` leaving out what it matches, or, where `testRegex` is set, that one of its expressions matches, and that no `testPathIgnorePatterns` expression matches, `/node_modules/` where unset. Where unset, `testMatch` is `**/__tests__/**/*.[jt]s?(x)` and `**/?(*.)+(spec|test).[tj]s?(x)` in version 29 and `**/__tests__/**/*.?([mc])[jt]s?(x)` and `**/?(*.)+(spec|test).?([mc])[jt]s?(x)` from version 30, and `moduleFileExtensions` is `js`, `mjs`, `cjs`, `jsx`, `ts`, `tsx`, `json` and `node`, with `mts` and `cts` from version 30. A configuration that sets both `testMatch` and `testRegex` names no test file.
- AVA, versions 6 to 8 ([lib](https://github.com/avajs/ava/tree/main/lib)): the configuration is the first of `ava.config.js`, `ava.config.cjs` before version 8 and `ava.config.mjs` in the nearest directory at or above the manifest's, no higher than the repository's, that holds one, or the manifest's `ava` member; both, or a configuration that exports a function, name no test file. The extensions are the `extensions` array or object keys, else `cjs`, `mjs` and `js` before version 8 and `mjs` and `js` from it. The test files are the files below the manifest's directory with one of the extensions that the `files` globs match without regard to case, a glob starting `!` leaving out what it matches, and that hold no segment starting with `.`, no `.git`, `.log`, `.nyc_output`, `.sass-cache`, `.yarn`, `bower_components`, `coverage` or `node_modules` directory, and no name starting with `_`. Where `files` is unset or lists only exclusions, the defaults are added: `test.E`, `{src,source}/test.E`, `**/__tests__/**/*.E`, `**/*.spec.E`, `**/*.test.E`, `**/test-*.E`, `**/test/**/*.E` and `**/tests/**/*.E`, `E` standing for the extensions, less the files below a `__helper__`, `__helpers__`, `__fixture__` or `__fixtures__` directory under `__tests__` and below a `helper`, `helpers`, `fixture` or `fixtures` directory under `test` or `tests`. A command running AVA only narrows these, so none is read.

Node.js's test runner needs no row: in every manifest the analysis reads, each command of `scripts` that runs `node` with `--test`, as the second layer of [roots.13](roots.md) reads it, the command a launcher it reads hands on included, runs the files its operands, each a glob read against the command's directory, match, or, with no operand, the files Node.js's default patterns match: `**/*.test.E`, `**/*-test.E`, `**/*_test.E`, `**/test-*.E`, `**/test.E` and `**/test/**/*.E`, with `E` standing for `{cjs,mjs,js}`, and for `{cts,mts,ts}` too unless the command writes `--no-strip-types` ([Running tests from the command line](https://nodejs.org/api/test.html#running-tests-from-the-command-line)).
