# The program

Rules `program.1` to `program.39` of [the analysis](../analysis.md). A rule is cited by its id, which is never reused for another rule.

## The target kind

**program.1** The configuration's `target.kind` names one kind for the whole target, or one kind for each language. Every rule of the Contract that reads the target kind, on this page, in [`kinds.json`](../../kinds.json), in [`exemptions.json`](../../exemptions.json) and in the configuration keys, reads for a declaration the kind of the declaration's language: a rule stated for a library holds for a declaration whose language has the kind `library`, and a rule stated for an application for one whose language has the kind `application`. So in a target whose Go code is an application and whose TypeScript code is a library, the published API is the TypeScript code's alone. The published API as a root, the reachability class of its findings and the minimum confidence that withholds them, `consumers.complete`, the published-package note and the conversions an outside program writes are among those rules, and the rule is not limited to them. An analysis reads the member of its own language, and an analyzer that claims two languages applies each member to its own language's declarations. A cross-language edge reads no kind, because each of its sides is decided by the analysis of that side's language. A report states the kind of the languages it covers, as [`report.schema.json`](../../report.schema.json) states.

**program.2** The program is the source the analysis holds for the target and its declared consumers under each configuration of the run. A run that holds no program, a target with no source file of its language or a configuration that names no file, ends with exit code 3, a setup failure of the class `no-program`. A TypeScript target holds no program when it holds neither a compiler configuration nor a JavaScript file a program is formed from under "JavaScript projects".

**program.3** Where a configuration sets `baseUrl`, itself or through a configuration it extends, the analysis resolves its imports as the compilers before version 7 resolve them, which read `baseUrl` and version 7 does not: each `paths` target is read against that `baseUrl`, and a specifier no other pattern of `paths` maps is looked up below it, as a `*` pattern mapping to `<baseUrl>/*` would, which the configuration's own `*` pattern replaces.

## The Go modules of a target

**program.4** The Go program of a target is every Go module the target holds. A target whose root holds a `go.mod` file is that module and every module below it that the workspace file listing the target lists, and any other module rooted below it is a module of its own, which the target's build reads as a dependency or not at all. A target a `go.mod` file above it governs is a directory of that module, and no module below it is a module of the target. A target whose root holds none and that no `go.mod` file above it governs is every module rooted below it: each directory holding a `go.mod` file, searched in no `vendor`, `testdata` or `node_modules` directory and in no directory whose name starts with `.` or `_`. Each module loads from its own directory with its own module file and its own build list, and one report covers them all: every position is relative to the target root, a reference from one module of the target to a declaration of another counts where the first builds the second from the second's directory, through a `replace` directive or a workspace, and a directive of a module file is reported against that file, scoped by its module path. A declaration of a copy outside the target that shares a module's path, a module cache entry among them, is no declaration of the target. The derived Go matrix reads the files of every module. The report's target identity is the module path of the module rooted at the target root, else the scope document's `target.id`, else the module path of the first module in directory order.

**program.5** A module that a `go.work` file at or above its directory lists among its `use` directives loads through that workspace, as `go build` run in that directory does, and every other module the workspace lists outside the target is a dependency of it, of which nothing is reported. A module the nearest workspace file does not list loads with no workspace, whatever the environment sets.

**program.6** A module the search below a target root that holds no `go.mod` file finds, and that does not load, a setup failure or a load error, is dropped: the run analyzes the modules left and the report carries a `module-not-loaded` note naming its directory. When every module is dropped the first failure ends the run as any setup failure does. A module the target is, and a module its workspace file lists, are named by the target and end the run when they do not load.

**program.7** Below the target root, whether or not it holds a `go.mod` file, a module of its own that is no module of the target and that requires a module of the target and replaces it with that module's directory builds against the target's tree, so the run loads it as a consumer: its references count as a declared consumer's do, nothing of it is reported, and it is no declared consumer, so it changes no reachability class and the report's `consumers` does not name it. One that does not load is dropped with a `module-not-loaded` note. A module dropped this way, or by the search below a target root that holds no `go.mod` file, keeps its note, and each of its scripts is a program run by naming the file, as a `main` file under the `ignore` tag is: a file other than a test file, below the module's root in no module of its own and in no directory the search leaves out, that the configuration builds with or without `ignore`, whose package clause is `main` and that declares a function `main`, in a directory where another such file declares `main` too, so no build of its package compiles it. Each declaration of the target a script names is a root. Its names resolve as they do when the toolchain builds that file alone from the module's directory, and a name that does not resolve roots nothing. A module that requires a published version of the target is no consumer of this tree. A module that builds against the target's tree below a directory whose name starts with an underscore is a consumer all the same. A package of a module of the target below such a directory, an example program's among them, is one no pattern ending in `/...` matches, so no build of the module compiles it, and the run loads it as a consumer of its module in the same way: its references count, nothing of it is reported, and one whose imports do not resolve counts nothing. This holds for every module of the target: a module the search below a target root that holds no `go.mod` file finds as much as the module a target root holds and one its workspace file lists.

**program.8** A module the workspace listing the target lists outside it, which a report names only from a run directory that holds it, still counts its references when the report cannot name it, whatever source gave the scope, unless the scope declares it a consumer: one whose `go.mod` requires a module of the target is loaded through the workspace as a module below the target that builds against the target's tree is, and the report's `consumers` does not name it. One whose `go.mod` the go command cannot read ends the run, as a module the target names does when it does not load, because every load through that workspace reads that file. One whose `go.mod` the go command reads and the analysis cannot, a directive newer than the analysis among them, may require any module of the target, so it is dropped unloaded: every module of the target has it as a consumer the run did not analyze, and the report carries a `module-not-loaded` note naming the target root.

**program.9** A module of the target that a dropped module's `go.mod` requires has it as a consumer the run did not analyze, so every exported declaration of an importable package of that module has the reachability class `possible`; a module whose dropped neighbour's `go.mod` cannot be read is treated as required.

**program.10** Every position a setup failure line names is relative to the target root, a module's below it included.

## Component files

**program.11** A derived TypeScript matrix holds the test files the test runner compiles. A file `ts.test_files` names that no derived configuration's file list holds joins the configuration of the nearest compiler configuration file at or above its directory that the matrix holds, `tsconfig.json` first where one directory holds several and the others in bytewise order of their names, as a file that configuration's file list names, because the test runner compiles the file with those options. It joins only where the nearest `package.json` at or above its directory is the nearest `package.json` at or above that compiler configuration file's directory, or neither has one, because a file below a manifest the configuration does not share belongs to another package, whose own test runner compiles it. A file with no such configuration at or above it, or whose nearest `package.json` that configuration does not share, joins none. A matrix the configuration document declares is the maintainer's, and no file joins it this way.

**program.12** A derived TypeScript matrix holds each compiler configuration under the target root and each configuration below the target root that one of them references, transitively, as the compiler reads the reference: a path that names no `.json` file names the `tsconfig.json` in that directory. A configuration below the target root that a declared configuration references and the configuration document does not declare ends the run, because the compiler builds a referenced project's sources into the program that references it without reporting their diagnostics. A referenced configuration outside the target root is an outside project: the compiler builds its sources into the referencing program as declarations outside the analysis, so a reference into them counts as a reference to a dependency's declaration does, and nothing about them is reported.

**program.13** A file whose name ends with an extension `ts.component_extensions` lists is a component file. A component file is in a project's program when the project's file list names it or an import of the program resolves to it, and an import of a component file resolves to that file. The analysis reads a component file as markup holding script blocks, and it parses no markup:

- **program.14** A `<script>` element whose start tag begins a line at the top level of the file is a block. Its content, up to the matching `</script>` end tag, is source of the language its `lang` attribute names: `ts` and `tsx` are TypeScript, and a block with no `lang`, or with `js` or `jsx`, is JavaScript.
- **program.15** A comment, which holds no block, ends as the parser of the file's framework ends it. In a file whose extension is `.svelte` it ends at the first `-->` after its opening `<!--`. In any other component file it ends at the first `-->` or `--!>` that starts after its opening `<!`, the opening dashes counted, so `<!-->` and `<!--->` are whole comments. A `{` that no `}` closes inside a start tag hides no later block. In a `.vue` file it is a character of an attribute name or value, and the tag ends at the next `>`. In any other component file the braced value ends at the next `>` or before a `<script` start tag that begins a line, whichever comes first. Either way, a start tag holding such a brace ends before a `<script` start tag that begins a line.
- **program.16** A file whose first line is `---` holds a frontmatter block: the lines after it up to the next line that is `---` are a TypeScript block.
- **program.17** A `<script>` element with a `src` attribute, in its self-closing form or with an end tag, is a namespace import of the file `src` names, positioned at the attribute. It references every export of that file, as a retained namespace import binding does.
- **program.18** The blocks of one file are one module, read in file order, of the strongest language any block names, in the order TSX, TypeScript, JSX, JavaScript. A file that holds no block is an empty module.
- **program.19** A `<script` start tag that begins a line and is not read as a block, or that begins a line inside a block, is printed as a warning on standard error naming the file and the line, and the file is analyzed without it.

**program.20** Every top-level binding of a component file's module is retained while the file is live, because the markup may use it: a declaration, and an import binding, which is resolved to the declaration it names, a namespace import to the module it names, and a named or default import to the export it names, followed along the export's re-exports. Where an import binding resolves to a module, as a namespace import does and as a named or default import of `export * as ns from` or `export * as default from` does, every export of that module counts as used, because the markup may read any of them and the analysis parses no markup. No finding is reported about a retained binding, `DS1503` included. Everything the module references counts as a use. The markup of a live component file is template text for the `template-field` exemption of [`exemptions.json`](../../exemptions.json), so a member whose name the markup holds is retained by that class. A type error in a block is a type error under the rule below.

## Workspace packages

**program.21** A TypeScript workspace is declared by the `packages` sequence of a `pnpm-workspace.yaml` file, or by the `workspaces` member of a `package.json`, an array of globs or an object whose `packages` member is one. The analysis searches for the declaration from the target root upward to the first directory holding one, and no further than the root of the repository that holds the target. A member is a directory the globs name, minus the globs a `!` negates and never under a `node_modules` directory, that holds a `package.json` with a `name`; the directory holding the declaration is a member too.

**program.22** An import whose package name is a member's resolves to the member's source, so a workspace is analyzed with no build and no path mapping:

1. **program.23** Where the package manager linked the importing directory to another package of that name, and that package is not the member, the import keeps the resolution the compiler gives it, and so does an import from outside the member that the member's name does not link.
2. **program.24** Otherwise, where the compiler's own resolution reaches a source file inside the member, that file stands. A declaration file stands only when no configuration of the member writes its output where the file is.
3. **program.25** Otherwise the member's manifest decides: the `exports` entry the import's subpath selects, the exact key first and then the longest pattern, its targets tried in condition order; with no `exports`, `types`, `typings`, `main` and `module` for the package itself, or the subpath below the member's directory. Each target is read back to its source through the member's emit mappings: each compiler configuration of the member maps its output directory and its declaration directory to its root directory, or, with no root directory, to the configuration's own directory and then to the common directory of its input files, and an output file maps to the source file of the same name with the source extension the output extension stands for. A target that is an existing file and neither a TypeScript source nor compiler output, a stylesheet or an image, is no module with a source: the import keeps the resolution the compiler gives it, and a failure to resolve it is a type error of the importing statement, not a `workspace-member-without-source`.
4. **program.26** An import no candidate reads back to a source file is the setup failure `workspace-member-without-source` below.

**program.27** A file below the workspace's root that git ignores, by the `info/exclude` file of the repository holding that root, in its common git directory, where a linked worktree's or a submodule's `.git` file leads, and by the `.gitignore` files from the repository's root down to the file's own directory, read as git reads them, is output a build left in the tree, not a file the member's sources or an install wrote. Where the compiler's resolution, or a target, reaches one inside a member, rule 2 does not keep it, and it reads back, after the emit mappings, to the source its path mirrors: its path below one of its directories inside the member, the deepest first, read below the member's own directory with the source extension its output extension stands for, a source file no `.gitignore` ignores. This holds for a member no compiler configuration builds as well. An ignored file whose path mirrors no source keeps the resolution the compiler gives it.

**program.28** An import is read from the package of its file: the member that holds the file, or, where no member does, the package of the nearest `package.json` at or above the file below the workspace's root, so a package below the target that no workspace lists and whose manifest depends on a member, an example among them, imports the member as a member does and is a loaded consumer of it. A reference from every program that holds a member's file counts, so a declaration a sibling member uses is live. A finding about a member's file is reported only from a configuration that owns the file, one whose own file list names it; a configuration that holds the file only because an import reached it contributes references to it and no verdict about it. A member's manifest entries are roots as the target's own are. A member whose manifest does not mark it private is a published package: its manifest entries, read back to their source, are its published API, so in an application target it is a library inside the target and the confidence rule below gives its published API the class a library's published API carries.

## Nested packages

**program.29** The manifests the analysis reads are the target's `package.json`, each workspace member's, and each nested package's. A nested package is a directory below the target root, in no `node_modules` directory, that holds a `package.json` and lies at or above a source file of the program or a compiler configuration file of the run. A `package.json` above no such file governs nothing the run holds, the manifest of a test fixture or of an example that every compiler configuration leaves out among them, so it is not read. Every rule of this page that reads a manifest the analysis reads reads each of them against its own directory: script entries, manifest entries, configuration files, the application of convention rows, and the dependencies `DS1701` in [`kinds.json`](../../kinds.json) judges. So, under the same configuration document, a run at the target root applies to a nested package's files and manifest every row, root and use that a run whose target is that package applies. The root run adds what only the root holds: a workflow step, an HTML entry file outside the package, a reference from a file outside it, and a row an enclosing nested package's manifest applies, which matches the files of a package nested inside it too. A configuration document a nested package holds is not read by a run at the root, because a run reads one configuration document, so the two runs differ as their documents do.

## Type errors

**program.30** A type error the compiler reports in source the program holds does not end the run. The innermost function, method, accessor, constructor, arrow function or function expression whose source holds the error's position is not evaluated, or the class member or the file-level statement holding it where no function does: nothing is reported about it or about any part of it, every reference in it the compiler resolves still counts, and every declaration an expression of it that does not resolve could reach is retained, so the skip can only withhold a finding. A diagnostic the compiler marks as reporting unnecessary code is not a type error for this rule, in any file. Nor is a diagnostic about where the configuration places a file, which changes no type a statement carries: in TypeScript an output that would overwrite an input (TS5055, TS5056), a file outside `rootDir` (TS6059) and a file a composite project does not list (TS6307). Each type error that skipped something is listed in the report's `type_error_skips` with its file, its line and the compiler's message, printed on standard error, and rendered as a warning annotation by the `github` format; the exit code follows the findings.

**program.31** A type error in a dependency's declarations, outside the program, is not the program's and skips nothing.

**program.32** A dependency package whose every Go file the analysis's cgo-disabled reading excludes, and that the configuration builds with cgo enabled, is a package of the program the analysis holds no declaration of: a reference to one is a type error of the referencing source, under the rule above, and no setup failure.

## Unanswered questions

**program.33** A question the analysis asks its type checker that the checker fails to answer is never read as an answer. Every declaration the answer could have made live is held: no finding is reported about it, every liveness relation treats it as live, and a declaration that reads a held binding by name is held too. An unanswered question holds a declared dependency only where its answer is the resolution of a module specifier, and then each dependency a manifest at or above the file that writes the specifier declares. Each configuration in which at least one question went unanswered is listed in the report's `unanswered_questions` with the number of questions and of declarations held.

## JavaScript projects

**program.34** A file named `jsconfig.json`, or `jsconfig` followed by any name and `.json`, is a compiler configuration, read wherever a `tsconfig*.json` file is and opened as written, with the defaults the compiler gives a `jsconfig` file, which read JavaScript files. In a derived matrix, a `jsconfig.json` in a directory that also holds a `tsconfig.json` is not opened, because the compiler's editor host reads that directory's `tsconfig.json`; one the configuration document or the scope names is opened.

**program.35** Where the configuration document declares no project, a JavaScript file, one whose name ends with `.js`, `.jsx`, `.mjs` or `.cjs`, below the target root that no derived configuration's file list holds and no test file rule joins to one is a file of a program the analysis forms for it, unless it is in a directory the language's row of [`languages.json`](../../languages.json) skips, git ignores it as `program.27` reads git's rules, it is below the output directory or the declaration directory of a configuration of the run or below a directory an applied convention row names as generated, or it is minified: its name ends with `.min.js`, `.min.cjs` or `.min.mjs`, or it holds at least 10,240 bytes in lines whose mean length exceeds 500 characters. Such a file is build output, so a bundle's copy of a module keeps nothing live; a minified file a program reaches by import is a generated file, whose declarations the `generated-file` class of [`exemptions.json`](../../exemptions.json) retains. An ignore file that cannot be read ignores nothing, and the run names it on standard error. The files are grouped by the nearest directory at or above each of them, up to the target root, that holds a `package.json`, and by the target root where none does. A `package.json` that does not parse, or that the run cannot read, still bounds its group: what it declares is unanswered, so it declares no dependency and no entry point, the group's configuration is listed in the report's `unanswered_questions` with one question, and the run names the file on standard error, with the read's error for one it cannot read. Each group is one configuration of the matrix, built as a configuration the analysis writes in the group's directory, which no file on disk holds and whose path below the target root is the configuration's `project`; its `id` is the path of the group's `package.json` below the target root, or `.` for a group with none. The configuration lists exactly the group's files and reads them unchecked, with no emit, the library declarations unchecked, no JavaScript of an installed package loaded and every type package visible. A group in a workspace member's directory is one of that member's configurations, so an import of the member from another member reads the group's files as source. A declared consumer that holds no compiler configuration is loaded through the programs formed the same way below its root: where the consumer sits in a workspace, an import of one member from another reads the member's group as source, as the target's members do, and a consumer whose JavaScript imports declared dependencies of which none is installed, as `program.37` reads them, ends the run with the setup failure `missing-consumer`. A program formed this way that does not load is dropped as a derived configuration is.

**program.36** The module system of a program `program.35` forms follows the runtime its package is written for, as the convention rows, the group's manifest and its command strings say. A group that a convention row of a bundler applies to, through the group's manifest or the manifest at the root it is formed below, the target's or a consumer's, resolves its modules as a bundler does and keeps each file's module syntax. Otherwise a group whose manifest names `main`, `exports`, `bin`, `type` or `engines.node`, or one of whose manifest's command strings, its `scripts` and nodemon's `exec`, runs a file with `node`, as the second layer of `roots.13` reads that command, resolves its modules as Node does. There a file's extension and the `type` of the nearest `package.json` decide its module format, as [Node](https://nodejs.org/api/packages.html#determining-module-system) decides it: a `.mjs` file is an ES module, a `.cjs` file a CommonJS module, and a `.js` file an ES module where that `type` is `module` and a CommonJS module otherwise. A command `roots.13` does not understand, a `node` command that runs no file, and a file another runtime runs, `tsx` or `ts-node` among them, say nothing of the runtime. Any other group resolves as a bundler does, so a file with no module syntax is a classic script whose top-level declarations are globals, as a browser loads it.

**program.37** A JavaScript file of a program that does not check its JavaScript files may hold a module specifier that resolves to no file on purpose, so such a specifier is no setup failure, in a file a `// @ts-check` comment checks too. A relative specifier, one that is `.` or `..` or starts with `./` or `../`, that resolves to no file references nothing, and the report carries an `unresolved-specifier` note naming it, unless it names a path below the output directory or the declaration directory of a configuration of the run, which is build output a build writes later. A specifier written inside the block of a `try` statement, or by a `require` call that is the left operand of an `||` or a `??` expression, parentheses around it aside, is an optional load, which notes nothing. A configuration whose JavaScript files import at least one dependency a manifest at or above the importing file declares, with no `package.json` that does not parse or cannot be read between them, and of which none resolves, has no installed dependencies, so its program is not the one the project runs: it ends with the setup failure `missing-module`, naming the importing file, the specifier and the install step, under the rule `setup-failures.1` states for a configuration of its origin.

**program.38** In a group `program.36` resolves as Node does, a relative specifier that resolves to no file is asked again as a bundler resolves it, and the file that resolution names is referenced at the class `possible`, because a loader hook, a test runner's transform or a bundler the analysis does not see may load it.

**program.39** A project entry of `analysis.configurations` may name a `package.json` below the target root. It names the program `program.35` forms for that directory, over the JavaScript files below it that no other entry's configuration lists and no nested `package.json` groups. An entry naming a `package.json` that is absent, or a directory, ends the run with exit code 3, as every declared entry does.
