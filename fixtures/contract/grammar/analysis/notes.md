# Notes

Rules `notes.1` to `notes.7` of [the analysis](../analysis.md). A rule is cited by its id, which is never reused for another rule.

**notes.1** A note is a hint about the run's setup that the analysis cannot decide. It is no finding: the findings beside it are reported as they would be without it, and it fails no run.

- **notes.2** `module-not-loaded`: a Go module below the target root that the run dropped because it does not load, as "The Go modules of a target" states. The note names the module's directory relative to the target root and carries no `key`, because no configuration key settles it; its message ends with the first line of the failure. A module the workspace listing the target lists outside it whose `go.mod` the go command reads and the analysis cannot is dropped too, as "The Go modules of a target" states, and its note names the target root, written `.`, with a message naming the module's directory relative to the target root.
- **notes.3** `published-package`: a Go package of an application, not a `main` package and not under an `internal` directory, that no file of another package of the target, no program of the target, under the `ignore` tag or a script of a dropped module, and no module or package the run loads as a consumer of its own tree imports. Outside programs may import such a package, and only the user knows whether they do; the note names the package's directory, relative to the target root and written `.` for a package at the root itself, and `roots.patterns`, the key that roots its published declarations.
- **notes.4** `unmapped-entry`: a manifest entry, a `main`, `module`, `types`, `browser` or `bin` member, an `exports` target or a `browser` replacement, that reads back to no source file of any configuration of the run, and by name, as Manifest entries reads a target back, to no file that `ts.entry_files` or another entry of the manifest roots. It roots nothing, so the findings its file would have rooted are reported; the note names the directory of the manifest, relative to the target root and written `.` for the root, and `ts.entry_files`, the key that names the file it is built from.
- **notes.5** `computed-load`: a TypeScript load by a computed path the analysis cannot resolve, as the reachability-class paragraph of Confidence states. The note names the directory of the file that writes the call, relative to the target root and written `.` for the root, carries no `key`, because no configuration key makes the loaded files known, and its message names the call's position.
- **notes.6** `unresolved-specifier`: a relative module specifier of a JavaScript file that resolves to no file, as `program.37` states. The note names the directory of the file that writes the specifier, relative to the target root and written `.` for the root, carries no `key`, because no configuration key makes the file exist, and its message names the specifier and its position.
- **notes.7** `unread-command`: a package whose command strings, the held text of `roots.13`, name, read as plain text as `roots.13` states, a file of a configuration that no root enters with every name it exports, so the analysis cannot tell what a command uses of it. Holding a named file keeps its exports; it never keeps a declaration that is unexported and unreferenced. Such a file itself and each name it exports are held, as `roots.13` states, so the findings about them are left out by that rule, not by the note, and every other finding about the file, a declaration that it does not export and nothing references among them, is still reported. The note names the package's directory, relative to the target root and written `.` for the root, carries no `key`, because no configuration key makes a command read, and its message names each such file, by its path relative to the target root. A package has one such note however many configurations hold its files and whichever of its command strings hold the text that names them.
