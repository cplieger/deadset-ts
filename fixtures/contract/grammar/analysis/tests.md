# Test code

Rules `tests.1` to `tests.10` of [the analysis](../analysis.md). A rule is cited by its id, which is never reused for another rule.

**tests.1** Test code is the test files and the test-support code. A test file is a Go file whose name ends with `_test.go`, and a TypeScript file `ts.test_files` names or an applied convention row's test-file property names. A test is a declaration of a test file, a test function the test runner calls among them. Test-support code is the code only tests reach: the largest set of Go packages and TypeScript files, none of them a test file and each carrying test evidence of its own language, such that a test reaches each member, no member holds a root, and every import of a member and every reference to a declaration of a member from outside it is written in a test file or in another member. A TypeScript file is a member only where it carries test evidence of its own: an import of a test runner or a test library, being the runner of each convention row that names test files, the runners and the assertion and mock libraries `@jest/globals`, `@playwright/test`, `ava`, `chai`, `expect`, `jasmine`, `jest`, `mocha`, `msw`, `nock`, `node:test`, `sinon`, `tap` and `uvu`, and every package of the `@testing-library` scope, or package imports, one or more, every one of them a package that the nearest manifest at or above the file declaring it declares under `devDependencies` alone and that no file outside the test files and the files only tests reach imports, a Node.js built-in module, bare or under the `node:` scheme, being no package. A test runner may inject its globals: a Vitest configuration file, `vitest.config.*` or `vite.config.*` with a JavaScript or TypeScript module extension, in a manifest's directory, whose default export, read as a convention row's configuration file is read, sets `test.globals` to `true`, gives every file the runner loads `describe`, `it`, `expect`, `vi` and the other names `vitest/globals` declares ([Vitest `globals`](https://vitest.dev/config/globals)). Each compiler configuration of the run whose nearest manifest's directory holds such a file, and from whose directory `node_modules/vitest/globals.d.ts` is found at or above it, is analyzed with `vitest/globals` added to its `types`, so a use of an injected global is no type error. A TypeScript file of a configuration whose program holds that declaration file, that calls one of those globals or reads a member of it, the name resolving to a declaration outside the target's files and to no import, declaration or parameter of its own, carries test evidence, as an import of the runner does. A TypeScript file only tests reach that carries no such evidence is production code, so a declaration of it only tests reference is reported under `DS1102`. A reference here is a name that resolves to the declaration, so a call through an interface method or a function value references no implementation. A Go package is here its files other than test files, so a reference from its own test files is from outside it. A test reaches a package or a file through a chain of imports and references that starts at the test, whatever members the chain passes through. So every chain that reaches test-support code starts at a test, however many members lie between: a package only another member imports is test-support code, and so is a package whose only users are its own test files. Production code a test calls stays production code, because a chain from production code or from a root reaches it too. A Go package carries test evidence when one of its files other than its test files imports the standard library's `testing` package or a package of the assertion, runner and comparison modules `github.com/google/go-cmp`, `github.com/onsi/ginkgo`, `github.com/onsi/gomega`, `github.com/stretchr/testify` and `gotest.tools`, the module path itself or a path below it, a major-version suffix such as `/v2` or `/v3` included, and then each of those files is test-support code where the package is a member. A module whose path only starts with one of those strings is no such module. Code with no test evidence of its own stays production code however few chains reach it, so a package only tests reach that carries none is production code a test uses: a declaration of it that only test code references is reported under `DS1102`, one nothing references under the unused code its visibility selects, and a reference from it is a production reference. A file or package only tests reach that carries test evidence but is no member, because a file or package only tests reach that is no member imports or references it, is production code a test uses as well. Evidence is a property of the code, never of its file name or its directory, so no name or location makes code test-support code or keeps it out. A Go `init` function and a blank declaration run because their package is loaded, so neither is a root for this rule. A Go package or a TypeScript file a library's published API reaches is not test-support code, because outside programs may import it. The analysis classifies code by the chains that reach it and does not judge whether a test is a good one, so a test that reaches no production code is not reported for that.

**tests.2** Test code is judged with the tests:

- **tests.3** A reference from test code is a test reference, and a production sweep, which counts no test reference, judges no declaration of test code.
- **tests.4** A test function the test runner calls is a root. In Go it is a test, a benchmark, an example or a fuzz test of a test file, or `TestMain`. A method a suite runner calls by reflection is one too: for each call of a suite runner, the value it passes as the suite, where its static type is no interface, has each exported method of its method set that the target declares and the runner's rule names rooted, a method promoted through an embedded field included. testify's `Run` of `github.com/stretchr/testify/suite` takes the suite as its second argument and calls every method whose name opens with `Test`; gocheck's `Suite` of `gopkg.in/check.v1` takes it as its argument and calls every method whose name opens with `Test` or `Benchmark`, and `SetUpSuite`, `SetUpTest`, `TearDownTest` and `TearDownSuite`. A suite passed as an interface value roots nothing, because its dynamic type is not known. In TypeScript the runner loads a test file and calls what its top level registers, so the file's top level and every function its export table names are roots, and so is every export of a file below a `__mocks__` directory, which the runner puts in place of the module it mocks. Any other export of a test file is no root: it is judged as a declaration of a test file that is no root, so one nothing references is reported, and one only its own file references is reported under `DS1503`. Such a root is reported only under `DS1103`. A Go `init` function and a blank declaration of a test file are roots as they are in production code, because they run when the test binary loads their package. Neither is judged under `DS1103`.
- **tests.5** A declaration of a test file that is no root is reported under `DS1103` where that kind's rule holds for it. Otherwise it is reported when nothing references it, under the code a production declaration with the same shape carries: `DS1201` for an interface and the unused code its visibility selects otherwise. A declaration of a test file that only reported declarations of test files reference falls with them, in their dead component. A production declaration such an unreferenced declaration references stays out of that component: its own references decide its code and its component, and the reference counts as a test reference.
- **tests.6** A declaration of test-support code is test code: a reference from test code keeps it live under both liveness relations, so it is reported under `DS1001`, `DS1002`, `DS1003` or `DS1201`, the code a production declaration nothing references carries, at `certain` only when nothing references it, and under `DS1103` where a declaration of a test file would be. An export of it that test code references and only its own file references is reported under `DS1503`, as such an export of a test file is, and its reachability class is not lowered for the test references that keep it live. A finding about one nothing references belongs to the dead component of the declarations it reaches. A declaration of test-support code that a test referencing a live target symbol also references counts as a live target symbol of every test that references it, so such a test is no test of dead code, and test-support code is no other target symbol when `DS1103` judges a test or a declaration of test-support code. A production declaration whose reachability class is `possible` because programs outside the analysis may use it, being published API of a library whose run declares no consumer, and in Go a declaration of a package no build links or an export of a unit a dropped module requires, counts as a live target symbol of every test that references it, so such a test is no test of dead code. The declaration is still reported at `possible`.
- **tests.7** A part of a declaration of test code, a parameter, a receiver, a result, a statement, a store or a case, is reported only while the declaration is live in the run that counts test references. A TypeScript part that no declaration holds, written in a file's top-level statements or in a function they pass or hold, belongs to the file and is judged while the file is live, so the parts of the callbacks a test file registers are judged in the run that counts test references, as the body of a Go test function is. A declaration of test code nothing live references is not judged, so none of its parts is reported, and a declaration of test code reported under `DS1103` or as unreferenced is reported whole.

**tests.8** A file the analysis classified as test-support code is counted in the report's `test_file_rules` under the rule `test-support`.

**tests.9** A Go package or a TypeScript file is test-support code only when no configuration of the run imports it from production code: a production import under one configuration makes it production code under every configuration.

**tests.10** Exemption evidence written in test-support code is test evidence, as evidence in a test file is: in the run that counts no test reference it holds nothing, and in the run that counts test references it holds what it names.
